# build.gradle.kts

> Source: [build.gradle.kts](../../../build.gradle.kts) · Last synced with code: 2026-09-30

## Role

The build definition: which compiler and plugins to use, which libraries the app and tests
depend on, and how tests run. Generated by Spring Initializr (the command is in the commit
"Generate the Spring Boot project with Spring Initializr") and then trimmed.

## Walkthrough

### The file is Kotlin: trailing lambdas

```kotlin
plugins {
    ...
}
```

**Kotlin:** `plugins { ... }` is a *function call*. Its only argument is a lambda, and Kotlin
lets a lambda that is the last argument move outside the parentheses. When it's the only
argument, the parentheses disappear entirely. So `plugins { }` is really `plugins({ })`.
Inside the lambda, `this` is a Gradle object (a "lambda with receiver"), which is why you can
call `id(...)` or `kotlin(...)` without a prefix. This pattern is called a **type-safe builder**,
and it's how Kotlin DSLs (Gradle, Ktor, kotlinx.html) read like configuration.

### Plugins

```kotlin
kotlin("jvm") version "2.3.21"
// Opens Spring-annotated classes: Kotlin classes are final by default, Spring needs to subclass some.
kotlin("plugin.spring") version "2.3.21"
id("org.springframework.boot") version "4.1.1"
// Supplies versions from Spring Boot's BOM, so most dependencies below have none.
id("io.spring.dependency-management") version "1.1.7"
```

**Kotlin:** `kotlin("jvm")` is shorthand for `id("org.jetbrains.kotlin.jvm")`. `version` is an
**infix function**: `a version b` means `a.version(b)`. Any single-argument function marked
`infix` can be called that way.

- **`kotlin("jvm")`**: runs the Kotlin compiler and targets the JVM.
- **`kotlin("plugin.spring")`**: Kotlin classes and functions are **final by default** (Java is
  the opposite; you have to write `final`). Spring sometimes creates a runtime *subclass* of
  your bean (a proxy) to add behavior, e.g. `@Transactional` or `@Configuration`, and it can't
  subclass a final class. This compiler plugin ("all-open") automatically makes classes with
  Spring annotations `open`, and their methods too, so we don't have to write `open` everywhere.

  **`final` isn't immutable.** `final`/`open` controls *subclassing and overriding*. Mutability
  is a separate question (`val` vs `var`), and a final class can have `var` properties. The proxy
  doesn't change your class's values; it **wraps method calls**, roughly
  `override fun purchase() { begin(); super.purchase(); commit() }`. It needs to be able to
  subclass the class *and* override each method. Without the plugin:
  - final class: Spring fails at startup ("Cannot subclass final class"). Loud, easy to find.
  - open class, final method: the proxy can't override the method, so it runs **without the
    transaction, and without any error**. That's the dangerous case.
- **`org.springframework.boot`**: adds `bootRun` (run from source) and `bootJar` (one runnable
  "fat" jar that contains all dependencies).
- **`io.spring.dependency-management`**: imports Spring Boot's **BOM** (bill of materials), a
  list of library versions tested together.

**Why:** we have no version catalog (`libs.versions.toml`). The BOM already pins nearly every
version, so a catalog would add indirection for no benefit.

### Group, version and the Java toolchain

```kotlin
group = "com.robertwoolbright"
version = "0.0.1-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(21)
    }
}
```

`group` and `version` are the project's Maven coordinates. They would identify the artifact
if we published it, and `version` ends up in the jar name. `SNAPSHOT` is the Maven convention for
"work in progress, not a release".

**Kotlin:** `languageVersion = ...` looks like a field assignment. Gradle properties are lazy
`Property<T>` objects, though, and Gradle's Kotlin DSL turns `=` into a call to `.set(...)`.
Older builds write `languageVersion.set(JavaLanguageVersion.of(21))`.

**Why:** a toolchain makes Gradle compile and test with JDK 21, whichever JDK is running Gradle
itself (Gradle finds or downloads one). Anyone who clones the repo builds with the same Java
version. The Kotlin plugin reads the toolchain too, so the bytecode targets Java 21.

### Dependencies: configurations

```kotlin
dependencies {
    implementation("org.springframework.boot:spring-boot-starter-flyway")
    ...
    developmentOnly("org.springframework.boot:spring-boot-docker-compose")
    runtimeOnly("org.postgresql:postgresql")
    testImplementation(...)
    ...
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}
```

The function name in front of each dependency (its *configuration*) decides where it's visible:

| Configuration | Visible to |
| --- | --- |
| `implementation` | app code at compile time and at runtime |
| `runtimeOnly` | runtime only; our code never refers to it by name |
| `developmentOnly` | `bootRun` only; left out of tests and of the jar |
| `testImplementation` / `testRuntimeOnly` | the same idea, for `src/test` |

**Spring:** a **starter** is a dependency that brings a coherent set of libraries plus the
auto-configuration for them. Spring Boot 4 split the starters into smaller modules, which is why
Flyway, JDBC and Web MVC each have their own starter and test starter.

### Test dependencies

```kotlin
    testImplementation("org.testcontainers:testcontainers-postgresql")
    // Checks MockMvc responses against inventory.yaml (the contract-validation test).
    testImplementation("com.atlassian.oai:openapi-request-validator-mockmvc:3.0.0")
    // Property-based testing (generators + checkAll) inside ordinary JUnit tests; not Kotest's runner.
    testImplementation("io.kotest:kotest-property:6.2.5")
```

**Gradle: an explicit version.** Most dependencies here have no version because Spring Boot's BOM
supplies one. The Atlassian validator isn't in that BOM, so its version is written into the
coordinate (`group:artifact:version`). Chosen 2026-09-30: it reads the YAML itself, so the test
can't drift from the contract, and it plugs into MockMvc as a `ResultMatcher`. Kotest's
property module (also 2026-09-30) is the same story: not in the BOM, so it's pinned here.

| Dependency | What it gives us |
| --- | --- |
| `spring-boot-starter-{flyway,jdbc,webmvc}-test` | Test support for each module, e.g. `@WebMvcTest` + `MockMvc` and `@JdbcTest`. They also pull in `spring-boot-starter-test`: JUnit Jupiter 6, AssertJ, Mockito. |
| `spring-boot-testcontainers` | `@ServiceConnection`, which turns a running container into DataSource settings. |
| `kotlin-test-junit5` | `kotlin.test` assertions (`assertEquals`, `assertFailsWith`) backed by JUnit Jupiter. The artifact keeps its old `junit5` name, but it runs fine on JUnit 6. |
| `testcontainers-junit-jupiter`, `testcontainers-postgresql` | Start a real Postgres in Docker for tests. |
| `openapi-request-validator-mockmvc` (Atlassian, `3.0.0`) | Checks MockMvc responses against `inventory.yaml` in [InventoryContractTest.kt](test/inventory/InventoryContractTest.kt.md). Not managed by Spring Boot's BOM, so it carries an explicit version. Formerly `swagger-request-validator-mockmvc`; 3.0 is built for Spring 7 and Java 21. It brings Jackson 2 along (`com.fasterxml.jackson`), which lives in different packages from the app's Jackson 3 (`tools.jackson`), so the two don't clash. (The one package they share on purpose is `com.fasterxml.jackson.annotation`: Jackson 3 still uses the 2.x annotations.) |
| `kotest-property` (`6.2.5`) | Generators (`Arb`) and `checkAll` for [InventoryPropertyTest.kt](test/inventory/InventoryPropertyTest.kt.md). **Why:** tests run against real Postgres instead of H2, an in-memory database that imitates
others. Our oversell protection depends on Postgres-specific behavior (`ON CONFLICT`, row locks
during `UPDATE`, `CHECK` constraints), and H2 imitates those imperfectly.

### Compiler options

```kotlin
kotlin {
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict", "-Xannotation-default-target=param-property")
    }
}
```

**Kotlin:** Kotlin's null safety (`String` can never be null; `String?` can) stops at the edge of
Java code, because Java types carry no nullability. Kotlin treats an unannotated Java type as a
**platform type**, shown as `String!`: you may treat it as nullable or not, and if you guess
wrong you get a runtime NPE. Many Java libraries annotate their APIs instead.

- **`-Xjsr305=strict`**: turns the JSR-305 annotations (`@Nonnull` / `@Nullable`) into real
  `String` / `String?` types, so a mistake becomes a compile error. Spring Framework 7 uses the
  newer JSpecify annotations, which Kotlin 2.1+ enforces by default; this flag covers libraries still
  on JSR-305.
- **`-Xannotation-default-target=param-property`**: in `class Q(@Ann val x: Int)`, the one
  `val x` is a constructor parameter, a property and a backing field all at once, so an
  annotation on it is ambiguous. This option puts it on the parameter, **and** on the property
  if the annotation is allowed to target a property; otherwise on the backing field. Java
  annotations such as `@NotBlank` or `@JsonProperty` can't target a Kotlin property, so they land
  on the parameter and the field. Those are the places Bean Validation and Jackson look.
  This will become Kotlin's default in a future release.

### Tests run on the JUnit Platform

```kotlin
tasks.withType<Test> {
    useJUnitPlatform()
}
```

Spring Boot 4 manages **JUnit 6**. The test API we write against (`org.junit.jupiter.api.Test`)
is the same Jupiter API as JUnit 5. `useJUnitPlatform()` tells Gradle to run tests through the
JUnit Platform rather than the legacy JUnit 4 runner.

**Kotlin:** `withType<Test>` uses a **reified type parameter**. On the JVM, generic types are
normally erased at runtime, but an `inline` function can mark its type parameter `reified` and
use it as a real class. So you write `withType<Test>` instead of Java's
`withType(Test.class)`. The trailing lambda then configures every `Test` task.

### A separate task for the load test

```kotlin
// Why: the load test runs for a fixed time (20 s by default), too slow for every build, so it has
// its own task. Considered always running it: that would make every `./gradlew build` slower.
tasks.test {
    useJUnitPlatform { excludeTags("load") }
}

// Runs only the @Tag("load") tests: ./gradlew loadTest [-Dload.seconds=60 -Dload.clients=100]
tasks.register<Test>("loadTest") {
    description = "Runs the HTTP load test against the real app."
    group = "verification"
    testClassesDirs = sourceSets.test.get().output.classesDirs
    classpath = sourceSets.test.get().runtimeClasspath
    useJUnitPlatform { includeTags("load") }
    shouldRunAfter(tasks.test)
    // Why: a load test is a measurement; rerun it every time instead of reusing the last result.
    outputs.upToDateWhen { false }
    testLogging.showStandardStreams = true
    for (key in listOf("load.seconds", "load.clients")) {
        providers.systemProperty(key).orNull?.let { systemProperty(key, it) }
    }
}
```

Added 2026-09-30 for [InventoryLoadTest.kt](test/inventory/InventoryLoadTest.kt.md) (Robert chose a
separate task over running it in every build).

**JUnit: tags.** `@Tag("load")` on a test class labels it. `excludeTags("load")` keeps it out of
the normal `test` task; `includeTags("load")` makes the new task run *only* tagged tests.

**Gradle: registering a task.** `tasks.register<Test>("loadTest") { ... }` creates a second task of
the same type as `test`. A new `Test` task doesn't know where the tests are, so it gets the test
source set's compiled classes (`testClassesDirs`) and classpath. `register` is *lazy*: the block
only runs if the task is actually needed. (The first version used
`val loadTest by tasks.registering(Test::class)`. With `--warning-mode all`, Gradle 9.7.1 reported:
"The 'val name by registering(Type::class) { }' property delegate syntax has been deprecated. This
is scheduled to be removed in Gradle 10. Use 'val element = register<Type>(name) { }' instead.")

**Gradle: `description` and `group`.** What `./gradlew tasks` shows: `loadTest` is listed under
"Verification tasks" next to `test`, with that description.

**Gradle: `shouldRunAfter(tasks.test)`.** If both are requested (`./gradlew test loadTest`), run the
fast tests first. Unlike `dependsOn`, it doesn't make `loadTest` run `test` on its own.

**Gradle: `testLogging.showStandardStreams = true`.** Gradle normally swallows what tests print.
This shows it, which is how the load test's `println` summary reaches the console.

**Gradle: `outputs.upToDateWhen { false }`.** Gradle normally skips a task whose inputs haven't
changed ("UP-TO-DATE"). For a measurement you want a fresh run every time.

**Gradle: passing `-D` through.** `./gradlew loadTest -Dload.seconds=60` sets a property in *Gradle's*
JVM, but tests run in a separate JVM. The `for (key in listOf(...))` loop handles
each supported option; `providers.systemProperty(key).orNull` reads it (null if not given), and
`systemProperty(key, it)` forwards it to the test JVM. `?.let { }` only runs when
it's there, so the test's defaults apply otherwise.

**Kotlin: `tasks.test { }`.** Configures the existing `test` task. The `withType<Test>` block
above still applies to both tasks; this adds the tag filter to one of them.
