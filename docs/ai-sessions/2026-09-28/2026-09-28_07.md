### Claude

The top of your function is fine. A handler for one of Spring's exceptions looks exactly like a handler for one of yours. What's missing is an **import**.

**Why this is the first handler that needed one:** `SkuNotFoundException` and `AddStockOverflowException` are in the same package as the handler (`...inventory.error`). Kotlin, like Java, lets you use anything in your own package without importing it. `MethodArgumentNotValidException` is Spring's class, so the compiler doesn't know that name until you import it. Add this with the other imports:

```kotlin
import org.springframework.web.bind.MethodArgumentNotValidException
```

It's `web.bind`, not `web.bind.annotation`. In VS Code you can usually put the cursor on the red name and press Ctrl+. to have it add the import for you.

That will make it compile. The tests will still fail for these reasons:

1. **Status code.** Both new handlers return `INTERNAL_SERVER_ERROR` (500). The contract and the tests expect 400. Which `HttpStatus` constant is that?
2. **Body on line 40.** It's still copied from the overflow handler. For this exception, `ex.message` is Spring's long internal description, not your `@Min` text. Hint from before: `ex.bindingResult.fieldError` holds the error for the field that failed. Its `defaultMessage` is the text you wrote in `@Min(message = ...)`. Both are nullable, so you need a fallback, and `?.` and `?:` are how you get one.
3. **Name.** `handleMalformedBody` doesn't match what this handler does. This exception means the JSON was read fine but failed validation (`quantity` is 0). A malformed body is handler #3, `HttpMessageNotReadableException`. A name like `handleInvalidQuantity` or `handleValidationFailure` says what happens.
4. **Docs.** The two new handlers need a KDoc and a `// Contract:` line, the same way `handleSkuNotFound` has them. The KDoc hook will also flag them when you save. The overflow fallback `"Overflow Guard Triggered"` describes how the check works internally, not what went wrong for the client. Since the exception always carries its message, the fallback will almost never show up, but it's worth making it readable.

Fix the import and the status first, then run the tests. The overflow test should turn green right away. The validation tests will pass once line 40 is fixed.

## #5: `require(quantity >= 1)` in the service

**The problem.** Right now "quantity is at least 1" is enforced in only one place, the `@Min` + `@Valid` check in the controller. That only protects requests that come in over HTTP. The service is a public function, and any Kotlin code can call it directly:

| Caller | Goes through `@Valid`? |
|---|---|
| `POST /inventory/{skuId}` | ✅ yes |
| a test, a scheduled job, a message consumer, the future purchase code | ❌ no |

If one of those passes `-5`, you get a confusing failure far from the cause: a Postgres "integer out of range" error, or a CHECK constraint violation, and in both cases a 500. The actual bug was "someone passed -5", and nothing says so.

**What `require` is.** It's a Kotlin standard library function, and here it's the same pattern in a different domain:

```kotlin
fun borrow(book: Book, days: Int) {
    require(days >= 1) { "days must be at least 1, was $days" }
    // ... only runs if the check passed
}
```

If the condition is false, it throws `IllegalArgumentException` with that message. In Java you'd write `if (days < 1) throw new IllegalArgumentException(...)` yourself, or use Guava's `Preconditions.checkArgument`. The `{ }` is a lambda, so the message string is only built when the check fails.

**Two checks for two audiences.** This is the part worth understanding, and it's a good interview answer:

| | `@Valid` / `@Min` (controller) | `require` (service) | `CHECK (quantity >= 0)` (database) |
|---|---|---|---|
| Protects against | a bad **client** request | a bad **programmer** call | anything that got past both |
| Result | 400, a friendly message | 500, which says "we have a bug" | 500 |
| Normally fires? | yes, whenever clients send bad input | **never**, if the code is correct | never |

So you would *not* add a handler that maps `IllegalArgumentException` to 400. If `require` ever fires, it's your fault, not the client's, and 500 is the honest answer.

**Against it:**
- The rule "1" now lives in two places, `@Min(1)` and `require(quantity >= 1)`.
- It never fires today, so it can feel like extra code.
- Arguably it belongs in the repository instead, since the SQL guard math is what breaks on a negative number.

**My take:** put it in the service. "You can't receive fewer than 1 unit" is a business rule, and the service layer is where business rules live. Purchase will need the same check, so the pattern will get used again soon.

**Test first.** Per our workflow, if you decide to do it, I'll first write a failing test showing that `inventoryService.receiveInventory("widget", 0)` throws `IllegalArgumentException`, and that nothing was written. Then you add the one line.

## #6: renaming `handleMinQuantity`

**A useful fact first:** Spring doesn't care what the method is called. The `@ExceptionHandler(MethodArgumentNotValidException::class)` annotation routes the exception, and nothing ever calls the method by name. So the name is only for people reading the code, which means it should describe what the method actually handles.

**What it actually handles:** *every* Bean Validation failure on *any* `@Valid` request body in the app, because the advice is global. Today that's only `@Min` on quantity. When you add the purchase endpoint, or a `@Max` rule, or a new request class with `@NotBlank`, they'll all end up in this method. At that point `handleMinQuantity` is misleading.

**The fallback has the same issue:** `?: "quantity must be at least 1"` is specific to one rule. Under a general name, a general fallback such as `"Invalid request"` fits better. In practice the fallback almost never shows, because a field error always has a message.

**Against it:** the specific name is easier to understand *today*, and YAGNI ("you aren't gonna need it") is a fair argument. But renaming costs about a minute, and nothing else in the code refers to the method by name.

**My take:** rename it to `handleValidationFailure`, and make the fallback general.

## The catch: your function has an expression body

Line 29 has this shape:

```kotlin
fun receiveInventory(...): InventoryItem = <one expression>
```

That `=` form (an **expression body**) only fits one expression, whose value is what the function returns. `require(...)` is a separate step that has to happen *before* that expression, so there's nowhere to put it. You need to switch to a **block body**, which uses `{ }` and allows several statements. The trade-off is that you have to write `return` yourself.

Here's the same conversion in a different domain:

```kotlin
// Before: expression body
fun borrow(bookId: String, days: Int): Loan = loanRepository.create(bookId, days) ?: throw BookUnavailableException()

// After: block body
fun borrow(bookId: String, days: Int): Loan {
    require(days >= 1) { "days must be at least 1, was $days" }

}
```

The three changes are:
1. `=` becomes `{`, and the function closes with `}`.
2. `require(...)` goes on the first line inside.

**YAML:** each level of indentation is one more segment of the property name, so this block is
the same as two flat properties:

```text
spring.jackson.deserialization.accept-float-as-int=false
spring.jackson.mapper.allow-coercion-of-scalars=false
```

`deserialization:` and `mapper:` are not settings on their own. They are **map properties**: Spring
Boot binds everything under them into a `Map<DeserializationFeature, Boolean>` and a
`Map<MapperFeature, Boolean>`, and applies each entry to the `JsonMapper` it auto-configures. The
key is a Jackson enum constant written in kebab-case: relaxed binding (see [property sources](#what-isnt-here))
turns `accept-float-as-int` into `ACCEPT_FLOAT_AS_INT`. Careful with symbols: `*` in YAML is an
alias reference, not a wildcard, and a stray one stops the file from parsing.

**Spring:** Spring MVC reads a `@RequestBody` with this same `JsonMapper`, so the settings apply to
every JSON request body in the app, not just `POST /inventory/{skuId}`.

**Why:** what each body does, checked against Jackson 3 with a `data class` holding `val quantity: Int`
(2026-09-28):

| Body | Jackson 3 defaults | With this block |
| --- | --- | --- |
| `{"quantity": "5"}` | **accepted as 5** (`ALLOW_COERCION_OF_SCALARS`) | rejected |
| `{"quantity": 1.5}` | **accepted as 1**, silently truncated (`ACCEPT_FLOAT_AS_INT`) | rejected |
| `{}`, `{"quantity": null}` | rejected: missing / null for a non-null `Int` | rejected |
| `[5]`, `{`, `{"quantity": 3000000000}` | rejected: not an object / malformed / out of `Int` range | rejected |

### Compiler options

```kotlin
kotlin {
    compilerOptions {
        freeCompilerArgs.addAll("-Xjsr305=strict", "-Xannotation-default-target=param-property")
    }
}
```

**Kotlin:** Kotlin's null safety (`String` can never be null; `String?` can) stops at the edge of
Java code, because Java types carry no nullability. Kotlin treats an unannotated Java type as a
**platform type**, shown as `String!`: you may treat it as nullable or not, and if you guess
wrong you get a runtime NPE. Many Java libraries annotate their APIs instead.

- **`-Xjsr305=strict`**: turns the JSR-305 annotations (`@Nonnull` / `@Nullable`) into real
  `String` / `String?` types, so a mistake becomes a compile error. Spring Framework 7 uses the
  newer JSpecify annotations, which Kotlin 2.1+ enforces by default; this flag covers libraries still
  on JSR-305.
- **`-Xannotation-default-target=param-property`**: in `class Q(@Ann val x: Int)`, the one
  `val x` is a constructor parameter, a property and a backing field all at once, so an
  annotation on it is ambiguous. This option puts it on the parameter, **and** on the property
  if the annotation is allowed to target a property; otherwise on the backing field. Java
  annotations such as `@NotBlank` or `@JsonProperty` can't target a Kotlin property, so they land
  on the parameter and the field. Those are the places Bean Validation and Jackson look.
  This will become Kotlin's default in a future release.
