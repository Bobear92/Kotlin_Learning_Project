### Claude

Step 4 is the `InventoryQuantity` DTO, which is the request body for `POST /inventory/{skuId}` (and for purchases later). It's a small file, but it has two decisions in it.

## What you're building

A new file next to `InventoryItem.kt`:
`src/main/kotlin/com/robertwoolbright/inventory/inventory/InventoryQuantity.kt`

The contract ([inventory.yaml:117-125](src/main/resources/openapi/inventory.yaml#L117-L125)) says it's an object with one required integer field, `quantity`, and `minimum: 1`.

[InventoryItem.kt](src/main/kotlin/com/robertwoolbright/inventory/inventory/InventoryItem.kt) has almost the same shape: study-notes line, package, one-line KDoc, `data class`. Start by copying that structure.

## The two things that matter

**1. `val quantity: Int`, not `Int?`**
Jackson throws for `{}` and `{"quantity": null}` because it can't put "nothing" into a non-null `Int`. That turns into `HttpMessageNotReadableException` and then `400 Invalid request body`. If you write `Int?`, both of those get through as `null` and reach your code. The non-null type does the "required" check from the contract for you.

**2. `@Min(1)` enforces `minimum: 1`**
- It's `jakarta.validation.constraints.Min`, from the validation starter you added in step 2.
- You put it directly on the constructor `val`. Normally Kotlin would attach it only to the constructor *parameter*, which the validator never checks. The `-Xannotation-default-target=param-property` flag in [build.gradle.kts:48](build.gradle.kts#L48) makes it land on the property too, and the validator reads it there.
- It does nothing by itself. It only runs when the controller marks the body `@Valid` (step 7). Until then it's just a label.

Parallel example in a different domain:

```kotlin
data class BookRating(@Min(1) val stars: Int)
```

## Decision for you: where does the message come from?

The tests expect exactly `quantity must be at least 1` for both `0` and `-5`.

- **Option A (my recommendation):** put it in the annotation, `@Min(value = 1, message = "...")`. The handler then just returns the error's message. The rule and its wording sit on the same line, and when purchases reuse this DTO they get the same message for free.
- **Option B:** use plain `@Min(1)` and have the exception handler build the text from the field name and the limit. It's more general, but the handler gets more logic, and you'd be building a sentence that already has a fixed, known wording.

## Documentation checklist

- Study-notes first line: `// Study notes: docs/learning/notes/main/inventory/InventoryQuantity.kt.md`
- KDoc on the class: what it is and where it's used (the request body for receive and purchase).
- A `// Contract:` comment for the `minimum: 1` rule.

Tell me whether you're going with A or B, write the file, and I'll review it. Nothing will turn green yet, because the tests need the controller too. This step is just about getting the file right.
