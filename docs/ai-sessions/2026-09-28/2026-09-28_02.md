### Claude

Step 2 is adding `spring-boot-starter-validation` to [build.gradle.kts](build.gradle.kts). It's a one-line change, and you type it.

### Why we need it

Your test at [InventoryControllerTest.kt:202](src/test/kotlin/com/robertwoolbright/inventory/inventory/InventoryControllerTest.kt#L202) expects `{"quantity": 0}` to return 400 `quantity must be at least 1`. We decided to handle that with **Bean Validation**: you put `@Min(1)` on the DTO field and `@Valid` on the controller parameter, and Spring rejects the request before your service runs.

Right now the project has none of the pieces for that:

- **The annotations** (`jakarta.validation.constraints.Min` and friends) aren't on the classpath, so `@Min` won't even compile.
- **The engine** (Hibernate Validator, the implementation behind the Jakarta Validation API) isn't there to check them.
- **The wiring:** once the starter is present, Spring Boot's auto-configuration registers a validator bean, and Spring MVC uses it for any `@Valid @RequestBody` parameter.

The starter adds all three in one dependency. The Java equivalent is the same Maven `<dependency>` you've probably used with Spring Boot before.

### What to do

1. Add one line to the `dependencies { }` block. Use the same form as the other starters: `implementation(...)`, group `org.springframework.boot`, artifact `spring-boot-starter-validation`. **Leave the version off.** The `io.spring.dependency-management` plugin fills it in from Spring Boot's BOM, which is why the other starters don't have one either (the comment on that plugin says so).
2. Reload Gradle in VS Code, or just run the build. To check it worked, open any `.kt` file and see if `import jakarta.validation.constraints.Min` resolves. Then delete the import.

### Something to know for step 4

The compiler flag already in the file, `-Xannotation-default-target=param-property`, matters here. When you write `@Min(1)` on a constructor `val`, Kotlin has to pick what the annotation attaches to: the constructor parameter, the property, or the field. Without the flag, `@Min` can land somewhere the validator never looks, and validation silently doesn't run. That's a classic Kotlin + Spring bug. The flag makes it apply to both the parameter and the property, so a plain `@Min(1)` works. We'll come back to this when you write the DTO.

### Claude

You're right that a SKU with 0 stock is valid, and the system already supports it. The `minimum: 1` is about something else. There are two different "quantities" in the contract, and they have different rules.

### Two schemas, two meanings

[inventory.yaml](src/main/resources/openapi/inventory.yaml) defines two schemas:

| Schema | What `quantity` means | Rule |
|---|---|---|
| `InventoryQuantity` (the **request body** for POST receive and POST purchase) | **How many units to add or remove** in this operation | `minimum: 1` |
| `InventoryItem` (the **response**, what's stored) | **How many units are on hand** | `minimum: 0` |

So the stock level can be 0, which is your "out of stock" case. A single delivery or purchase can't be 0 units.

### Where "out of stock" already lives

- The database allows it: `CHECK (quantity >= 0)` in [V1__create_inventory.sql](src/main/resources/db/migration/V1__create_inventory.sql).
- `GET /inventory/{skuId}` returns `{"skuId": "widget", "quantity": 0}` for a known SKU that's sold out. You wrote tests for that zero-stock lookup in the last feature.
- The purchase feature will get a SKU to 0: receive 5, buy 5, and the SKU still exists with quantity 0. It returns 200, not 404.

### Why the request can't be 0

"Receive 0 units" doesn't do anything. It's either a client bug or a no-op, and the contract's authors chose to reject it with a 400 instead of accepting it silently. It also blocks a side door: without the rule, `POST /inventory/new-sku {"quantity": 0}` would create a SKU without receiving any stock. With the rule, the only way a SKU comes into existence is a real delivery. It can only reach 0 later, through purchases.

Negative quantities are rejected for a more important reason: receiving -5 would really be an untracked purchase that skips the insufficient-stock check. It would also break the assumption your `addStock` overflow guard depends on (the walkthrough note says the guard only holds when quantity ≥ 1).

This is a good question to have a ready answer for in the interview ("why does the request require 1 when stock can be 0?"). Want me to add it to [interview-prep.md](docs/learning/interview-prep.md)?

### Claude

A small correction to the first part first: skipping a pointless query is a side benefit, not the reason. The reason is that `minimum: 1` is in the contract, and a "receive" that receives nothing doesn't make sense as an operation. We'd reject it even if the database call cost nothing.

### A new item that's out of stock

**This API can't do that, and it doesn't need to.** Look at what each endpoint's description says:

- `POST /inventory/{skuId}` is "Adds stock... If the SKU does not yet exist in inventory, it is created with the given quantity." Creating the SKU is a side effect of receiving stock, not a separate operation.
- `GET /inventory/{skuId}` returns "404 if the SKU does not exist."

So in this API, a SKU exists once stock has been received for it. Nothing in the contract registers a product without stock.

**In real systems the scenario is valid, but it usually belongs somewhere else.** A retailer like Nuuly typically keeps two separate things:

- **A product catalog:** "we sell this item, here's its name, size, price." A product can sit in the catalog before the first shipment arrives.
- **Inventory:** "we have N units on hand." That's this service. It only has to track stock, so it's fine for it to learn about a SKU when the first units show up.

"Known product, never stocked" is a catalog fact. "Stocked, now sold out" is an inventory fact, and this service does handle that one (quantity 0 after purchases).

**If Nuuly needed it in this service anyway**, the right move would be a separate endpoint, something like "register SKU." Relaxing `minimum: 1` on receive would be the wrong fix: it would make "receive" mean two different things, and it would break the contract.

One consequence worth knowing: a 404 from `GET` can't tell "never heard of this product" apart from "this product was never stocked." For an inventory service that's acceptable, because both answers mean you can't sell it.

This makes a good interview answer: it shows you read the contract closely and that you know where the service's responsibility ends. Want me to add both points (request quantity vs stock level, and catalog vs inventory) to [interview-prep.md](docs/learning/interview-prep.md)?

````
kotlin("jvm") version "2.3.21"
// Opens Spring-annotated classes: Kotlin classes are final by default, Spring needs to subclass some.
kotlin("plugin.spring") version "2.3.21"
id("org.springframework.boot") version "4.1.1"
// Supplies versions from Spring Boot's BOM, so most dependencies below have none.
id("io.spring.dependency-management") version "1.1.7"
```

**Kotlin:** `kotlin("jvm")` is shorthand for `id("org.jetbrains.kotlin.jvm")`. `version` is an
**infix function**: `a version b` means `a.version(b)`. Any single-argument function marked
`infix` can be called that way.

- **`kotlin("jvm")`**: runs the Kotlin compiler and targets the JVM.
- **`kotlin("plugin.spring")`**: Kotlin classes and functions are **final by default** (Java is
  the opposite; you have to write `final`). Spring sometimes creates a runtime *subclass* of
  your bean (a proxy) to add behavior, e.g. `@Transactional` or `@Configuration`, and it can't
  subclass a final class. This compiler plugin ("all-open") automatically makes classes with
  Spring annotations `open`, and their methods too, so we don't have to write `open` everywhere.

  **`final` isn't immutable.** `final`/`open` controls *subclassing and overriding*. Mutability
  is a separate question (`val` vs `var`), and a final class can have `var` properties. The proxy
  doesn't change your class's values; it **wraps method calls**, roughly
  `override fun purchase() { begin(); super.purchase(); commit() }`. It needs to be able to
  subclass the class *and* override each method. Without the plugin:
  - final class: Spring fails at startup ("Cannot subclass final class"). Loud, easy to find.
  - open class, final method: the proxy can't override the method, so it runs **without the
    transaction, and without any error**. That's the dangerous case.
- **`org.springframework.boot`**: adds `bootRun` (run from source) and `bootJar` (one runnable
  "fat" jar that contains all dependencies).
- **`io.spring.dependency-management`**: imports Spring Boot's **BOM** (bill of materials), a
  list of library versions tested together.

**Why:** we have no version catalog (`libs.versions.toml`). The BOM already pins nearly every
version, so a catalog would add indirection for no benefit.
````

```
## Design and failure modes

### What happens if two rows ever share the same SKU?

<details>
<summary>Answer</summary>

`findBySkuId` ends in `.list().singleOrNull()`. With two rows, `singleOrNull()` returns `null`
without throwing. The service then throws `SkuNotFoundException`, and the client gets
**404 "SKU not found: widget"** for a SKU that actually exists twice. That's a silent bug: the API
gives a wrong answer and nothing is logged.

It can't happen today because `sku_id` is the **primary key**, so Postgres rejects a second
`widget` row. The Kotlin code is correct *because of* the database constraint. Keeping the primary
key is the real fix.

If `sku_id` ever stopped being unique, the lookup would need reworking:
- **`.single()`** throws on two rows, so the bug would surface loudly as a 500 instead of a false 404.
  But it also throws on **zero** rows, which is the normal "not found" case, so on its own it would
  turn every missing SKU into a 500.
- A version that handles both cases: `val rows = ...list()`, then `null` when `rows` is empty,
  the item when there's one, and an error (such as `IllegalStateException`) when there are more.
- Which row is "right" is a data question, not a code question, so a duplicate should fail, not be
  picked arbitrarily with `firstOrNull()`.

| List | `singleOrNull()` | `single()` | `firstOrNull()` |
| --- | --- | --- | --- |
| `[]` | `null` | throws | `null` |
| `[a]` | `a` | `a` | `a` |
| `[a, b]` | **`null`**, silently | throws | `a`, silently |

<details>

### How do you prevent SQL injection?

<details>
<summary>Answer</summary>

The SKU comes straight from the URL, so it's untrusted. The query uses a named parameter,
`WHERE sku_id = :skuId`, bound with `.param("skuId", skuId)`. `JdbcClient` runs it as a JDBC

can never change the query's structure. `x' OR '1'='1` is just a string that matches no SKU.

Building the SQL with a string template (`"... WHERE sku_id = '$skuId'"`) would paste the value
into the SQL text, and the attacker's quote would close ours.
```
