### What you'll write (request-path order)

| # | File | Layer | What it does |
|---|------|-------|--------------|
| 1 | `build.gradle.kts` | build | Add `spring-boot-starter-validation`, for Bean Validation. |
| 2 | `application.yml` | config | Make Jackson strict: no float→int truncation and no `"5"`→`5` coercion. |
| 3 | `inventory/InventoryQuantity.kt` *(new)* | model | Request body: `data class InventoryQuantity(val quantity: Int)`, named after the contract schema, with a `@Min(1)` constraint. |
| 4 | `InventoryRepository.kt` | repository | `fun addStock(skuId: String, quantity: Int): InventoryItem?` does one atomic upsert: `INSERT ... ON CONFLICT (sku_id) DO UPDATE SET quantity = inventory.quantity + EXCLUDED.quantity WHERE <no overflow> RETURNING sku_id, quantity`. It returns the new row, or `null` when the add would overflow. |
| 5 | `error/<your name>Exception.kt` *(new)* | error | Thrown when adding stock would overflow. You pick the name. |
| 6 | `InventoryService.kt` | service | `fun receiveInventory(skuId: String, quantity: Int): InventoryItem` calls `addStock` and throws the overflow exception on `null` (same `?: throw` shape you used in `getInventory`). |
| 7 | `InventoryController.kt` | controller | `@PostMapping("/{skuId}")` taking `@PathVariable skuId` and `@Valid @RequestBody body: InventoryQuantity`. |
| 8 | `InventoryExceptionHandler.kt` | error | Four new handlers, all 400 `text/plain`: validation failure, unreadable body, unsupported media type, and your overflow exception. |

Why the overflow guard sits in the SQL `WHERE`: this is the same pattern purchase will use (`UPDATE ... WHERE quantity >= ?`). The database decides atomically, and "no row came back" means "rejected". There's also a nice detail inside the check: `a + b <= MAX` would itself overflow, so you rewrite it as `a <= MAX - b`.

### 400 message text (exact strings the tests will check)

- `quantity` < 1: `quantity must be at least 1`
- Unreadable body (malformed JSON, empty body, `{}`, `null`, `"5"`, `1.5`, `3000000000`): `Invalid request body`
- Wrong Content-Type: `Content-Type must be application/json`
- Overflow: `Quantity would exceed the maximum stock`

### Tests I'll write

- **`InventoryRepositoryTest`** (+7): creates a new SKU; adds to an existing SKU; adds to a zero-stock SKU; leaves other SKUs untouched (a decoy row); reaches exactly `Int.MAX_VALUE`; returns `null` with stock unchanged on overflow; creates a separate row for a different-case SKU.
- **`InventoryControllerTest`** (+~8): new SKU → 200 JSON; existing → summed total; `0` and `-5` → 400 with stock unchanged; one parameterized test over every unreadable body → 400 `Invalid request body`; wrong Content-Type → 400; overflow → 400 with stock unchanged; case-sensitive SKU.
- **`InventoryConcurrencyTest`** *(new, from the oversell plan)*: 50 threads race a first-time `addStock` on the same SKU behind a `CountDownLatch` start gate, and 50 threads race an add to an existing SKU. Both assert no exceptions and final = sum. `@RepeatedTest(5)`. This one can't be `@JdbcTest`: its per-test rollback transaction would hide the rows from the other threads.

### New concepts (coaching list + walkthrough agenda)

- **Kotlin:** annotation use-site targets (`@field:Min`), and how the project's `-Xannotation-default-target=param-property` flag affects them; plus request DTOs as data classes.
- **Spring:** `@PostMapping`, `@RequestBody`, Bean Validation with `@Valid`, and the three framework exceptions (`MethodArgumentNotValidException`, `HttpMessageNotReadableException`, `HttpMediaTypeNotSupportedException`) and how the advice turns them into responses.
- **Jackson 3:** coercion and strictness settings through `application.yml`.
- **SQL:** Postgres upsert (`ON CONFLICT ... DO UPDATE`, `EXCLUDED`, a conditional `WHERE`, `RETURNING`), why one statement is race-free, and how to write an overflow check that can't overflow itself.
- **Testing:** start gates, thread pools and `@RepeatedTest` for concurrency tests.

One choice for you: the plan puts the `quantity >= 1` check in the **controller layer via Bean Validation**. That's idiomatic Spring and it teaches use-site targets. The alternative is a manual check in the service that throws your own exception. It's simpler, and it also protects callers that skip the controller, but it's less idiomatic.

Yes, SQL can do math. `+`, `-`, `*` and `/` work anywhere SQL expects a value: in `SELECT`, in `SET`, and in `WHERE`. Postgres works the numbers out itself, inside the statement.

The key idea is that **you only parameterize values that come from Kotlin.** The value already in the database doesn't need a parameter. You refer to it by its **column name**, and Postgres reads it from the row as it runs the statement.

| Value | Where it lives | How the SQL refers to it |
|---|---|---|
| The quantity being posted | your Kotlin `quantity` variable | a parameter: `:quantity` |
| The quantity already stored | the row in the table | the column name |

### A parallel example: a library

The table is `books(isbn, copies)`, and the library receives 3 more copies of one book. First, a plain `UPDATE`:

```sql
UPDATE books SET copies = copies + :added WHERE isbn = :isbn
```

The right side of `=` reads the row's current `copies` (say 5) and adds the parameter (3). The left side says where to store the result (8). The read and the write happen in one statement, so another request can't sneak in between them.

### Why the upsert needs two names

In `INSERT ... ON CONFLICT DO UPDATE`, **two rows** are involved when the conflict happens:

1. the row already in the table (5 copies)
2. the row you tried to insert, which was refused because the key already exists (3 copies)

Both have a `copies` column, so a bare `copies` would be ambiguous. Postgres gives each one a name:

- `books.copies` is the existing row: **5**
- `EXCLUDED.copies` is the refused row: **3**

```sql
INSERT INTO books (isbn, copies)
VALUES (:isbn, :added)
ON CONFLICT (isbn)
DO UPDATE SET copies = books.copies + EXCLUDED.copies
RETURNING isbn, copies
```

This stores 5 + 3 = 8. The left side of `SET` stays unqualified (`copies`, not `books.copies`), because Postgres doesn't allow a table name there.

### Claude

Yes. `RETURNING sku_id, quantity` is exactly it.

The easiest way to think about it: **`RETURNING` is a `SELECT` column list stuck on the end of an `INSERT` or `UPDATE`.** Compare it with `findBySkuId`:

```sql
SELECT sku_id, quantity FROM inventory WHERE ...     -- findBySkuId: reads rows
INSERT ... ON CONFLICT ... RETURNING sku_id, quantity -- addStock: writes, then hands back the row
```

Both produce a result set with the same two columns. That's why your row mapper is identical in both functions: `rs.getString("sku_id")` and `rs.getInt("quantity")` read the columns by name, so the names after `RETURNING` must match what the mapper asks for.

Three details worth knowing:

- **It returns the row *after* the change.** With 5 in stock and 3 posted, `quantity` comes back as **8**, not 3. That's the contract's "Returns the updated inventory state".
- **Without `RETURNING`, an `INSERT` returns no rows,** only a count of rows changed. To get the new total without it, you'd need a second `SELECT`, and another request could change the row between the two statements. `RETURNING` gives you the value from the same atomic statement.
- **It only returns rows that were actually written.** When the overflow guard is false, nothing is written, so `RETURNING` returns nothing: 0 rows, then `singleOrNull()`, then `null`.

Java/JDBC comparison: without `RETURNING`, you'd call `executeUpdate()` and get back just an `int` row count. With it, you call `executeQuery()` and get a `ResultSet`, like a `SELECT`. That's why this function uses `.query { }` and not `.update()`.

### Claude

Good instinct: always ask what the edge values do to arithmetic. Here the subtraction is safe, and the reason comes down to **how big `EXCLUDED.quantity` can possibly be**.

### How big can it get?

`EXCLUDED.quantity` is whatever you put in `VALUES (:skuId, :quantity)`, and `:quantity` is bound from a Kotlin `Int`. An `Int` can't hold anything above `Int.MAX_VALUE`. A request like `{"quantity": 3000000000}` never gets this far: Jackson can't fit it into an `Int` and rejects the body. One of the unreadable-body tests checks exactly that.

So the largest possible value is `MAX` itself, and the subtraction stays in range:

| `EXCLUDED.quantity` (new) | `MAX − new` | Overflow? |
|---|---|---|
| 1 | 2,147,483,646 | no |
| 1,000,000 | 2,147,483,647 − 1,000,000 | no |
| 2,147,483,647 (`MAX`) | **0** | no |

Subtracting a positive number from `MAX` moves *down*, toward 0. Subtraction can only overflow by going below `Int.MIN_VALUE` (about −2.1 billion). Getting there from `MAX` would take subtracting more than 4.2 billion, which no `Int` can hold.

### The biggest case works correctly too

With `new = MAX`, the guard becomes `current <= 0`:
- **The SKU is at 0:** `0 <= 0` is true, so the total becomes `MAX`. That's allowed.
- **The SKU is at anything above 0:** false, so `null` comes back. That's right, because the total would be past `MAX`.

Your repository test does exactly this: the `"full"` SKU at `MAX` plus `Int.MAX_VALUE` returns `null`.

### The real risk runs the other way: negative numbers

What *would* break the guard is a **negative** `quantity`. `MAX − (−5)` is `MAX + 5`, which overflows, and Postgres throws "integer out of range". A negative "receive" would also quietly subtract stock whenever the guard didn't trip.

So the guard is safe **only because `quantity` is always at least 1**, and the repository doesn't check that itself. It depends on the controller's validation (`@Min(1)`, still to come) to reject 0 and negatives first.

That's a precondition worth stating in the KDoc for `addStock`, for example "`quantity` must be at least 1". Then anyone calling the repository from somewhere else (a future batch import, say) knows the rule. In the interview, "what does your overflow guard assume?" is a good question to be ready for, and the answer is "that quantity is positive, which the controller enforces."
