## Your decision: where does the message text live?

**A. In the exception.** Pass the text to `RuntimeException(...)`, just as `SkuNotFoundException` does. The handler returns `ex.message`, the same as `handleSkuNotFound`.
- Pro: it matches the pattern you already have, and all the error text sits with the exceptions.
- Con: the exception now holds wording meant for HTTP clients.

**B. In the handler.** The exception carries no message, or only a detail for logs. The handler writes the literal `"Quantity would exceed the maximum stock"` into the response.
- Pro: HTTP wording stays in the HTTP layer.
- Con: it breaks the pattern, and the text ends up far from the thing that failed.

**My recommendation is A**, for consistency. A reviewer who reads one handler will understand them all.

Something to know if you pick A: the body text doesn't include the SKU. If you give the class a `skuId` constructor parameter and never use it, Kotlin warns "parameter is never used". A class with no parameters is fine. The same shape in another domain:

