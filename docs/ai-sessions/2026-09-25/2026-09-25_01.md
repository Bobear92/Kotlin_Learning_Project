### Claude

You're on step 5, the controller. It's the last file for `GET /inventory`.

**The file:** `src/main/kotlin/com/robertwoolbright/inventory/inventory/InventoryController.kt`, in the same package as the other three.

**What it has to do:** the controller is the web layer and the top of the request flow (controller → service → repository). It takes an HTTP request and calls your `InventoryService`. Whatever it returns becomes the response body. The two tests in [InventoryControllerTest.kt](src/test/kotlin/com/robertwoolbright/inventory/inventory/InventoryControllerTest.kt) check:
- An empty table gives `200` and `[]` with `Content-Type: application/json`.
- Three rows give a JSON array of `{"skuId": ..., "quantity": ...}` sorted by SKU id. The comparison is `STRICT`, so the field names and the order must match exactly.

You get the sorting and the empty list from the code you've already written. Here's the good news: if the function returns `List<InventoryItem>`, Spring hands it to Jackson. Jackson turns it into that JSON automatically, using your property names `skuId` and `quantity`. The controller doesn't build any JSON itself.

**It has the same shape as your service:** one class with a dependency passed into its constructor, and one function with an expression body. Two things are new:

1. **A class-level annotation.** It tells Spring "this bean handles HTTP requests, and my return values *are* the response body." There are two candidates, `@Controller` and `@RestController`.
2. **A function-level annotation** that maps an HTTP method and a path to the function.

Two questions before you type:

1. Which annotation maps **GET** plus a path like `/inventory` to a function? (Hint: it's named after the HTTP method.)
2. Which one of `@Controller` and `@RestController` do we want, and why? Think about what Spring does with the return value in each case. With `@Controller`, a returned value is normally treated as the name of an HTML view to render.

**Documentation for this file:**
- The first line is the `// Study notes: docs/learning/notes/main/inventory/InventoryController.kt.md` link. The notes file itself gets written later, in `/sync-docs`.
- Add KDoc on the class and on the function. Start the function's KDoc with a verb, e.g. "Returns …".
- Put a `// Contract:` comment above the function's KDoc saying which part of `inventory.yaml` it satisfies. The KDoc has to sit directly on top of the function, so the `// Contract:` line goes above the KDoc, not between the KDoc and `fun`. Otherwise `check_kdoc.py` can't find the KDoc.
