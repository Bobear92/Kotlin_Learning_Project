## Does Kotlin favor a particular database?

No. On the JVM, Kotlin reaches databases the same way Java does, through JDBC drivers, so anything Java can connect to, Kotlin can too. What Kotlin does affect is which **data-access library** feels natural:

| Library | How it fits Kotlin |
|---|---|
| **Spring Data JPA / Hibernate** | The most common Java choice, and the worst fit for Kotlin. JPA expects mutable classes that can be subclassed and have a no-arg constructor. Kotlin classes are final and immutable by default, so you need compiler plugins (`kotlin-jpa`, `allopen`) to work around it. It also hides the SQL, which works against your learning goal. |
| **Spring Data JDBC / `JdbcClient`** | A good fit. It maps rows to plain immutable `data class`es, and with `JdbcClient` you write the SQL yourself. |
| **Exposed** (from JetBrains, the makers of Kotlin) | A Kotlin-native SQL DSL. It's nice, but it's another thing to learn and less common in Spring shops. |
| **jOOQ** | Type-safe SQL, and works well with Kotlin. Too much for four endpoints. |

So Kotlin shapes how you talk to the database, not which database you pick.

## Which database fits this project?

The data is just `skuId → quantity`. The hard requirement is correctness: a purchase must **never oversell**, even when two requests arrive at the same moment. That is what the reviewers will probe. A second constraint from the brief is that the app "must start and be testable with minimal setup."

| Option | Pros | Cons |
|---|---|---|
| **In-memory** (`ConcurrentHashMap`) | Needs no setup. You handle concurrency yourself with `compute()`, which is a good Kotlin lesson. | Data is lost on restart. Only works with a single instance, so it isn't how a real service would do it. |
| **H2** (embedded SQL) | Needs no setup and uses real SQL. | Its SQL dialect differs from production databases. Reviewers may see it as a toy. |
| **PostgreSQL** | Realistic, and the database enforces correctness for you (see below). | Needs Docker. |
| Redis / MongoDB / DynamoDB | — | No advantage here. Conditional decrements on Redis need Lua scripts, and document stores add nothing for a single integer per key. |

Postgres's strength here is that each operation is **one atomic SQL statement**:

```sql
-- Receive stock: create the SKU or add to it, atomically
INSERT INTO inventory (sku_id, quantity) VALUES (?, ?)
ON CONFLICT (sku_id) DO UPDATE SET quantity = inventory.quantity + EXCLUDED.quantity
RETURNING sku_id, quantity;

-- Purchase: succeeds only if enough stock exists; zero rows updated means 404 or 400
UPDATE inventory SET quantity = quantity - ?
WHERE sku_id = ? AND quantity >= ?
RETURNING sku_id, quantity;
```

With this, there's no read-then-write race and no locking code in Kotlin. The database guarantees you can't oversell, and it keeps holding true when the service runs as several instances. That's a strong answer to the inevitable interview question "what if two purchases arrive at once?"

## My recommendation: PostgreSQL + `JdbcClient`

- **Reasons:** It's realistic, correctness lives in the database, and the SQL is visible. You learn Kotlin data classes and Spring's JDBC support without Hibernate's magic in the way.
- **Setup cost:** Spring Boot's Docker Compose support starts Postgres automatically on `./gradlew bootRun`, and Testcontainers starts a throwaway Postgres for the tests. For a reviewer, the setup is "have Docker running," which is standard for a backend team.
- **Catch:** I checked your machine, and neither `docker` nor `java` is on the PATH in my shell. You'd need **Docker Desktop** and a **JDK 21** before we scaffold. The JDK is needed whichever database we pick.

If you'd rather avoid Docker, in-memory is also a defensible choice. You'd lose the realism and the database-enforced atomicity, and gain a lesson in Kotlin concurrency primitives.

### 1. Controllers: generate from the YAML, or write them by hand?

**My recommendation: write them by hand, and add a test that checks responses against `inventory.yaml`.**

- **Generated code hides what you want to learn.** `openapi-generator` would produce the interfaces, request and response classes, and much of the Spring MVC wiring: `@RequestMapping`, `@PathVariable`, `@RequestBody`, validation annotations. That's exactly the Spring behavior you want to understand and explain in the interview. It also produces a lot of dense boilerplate you'd have to read through.
- **We keep the contract safety anyway.** A contract-validation test (e.g. Atlassian's `swagger-request-validator` with `MockMvc`) checks each real response against `inventory.yaml`: status codes, content types (`text/plain` errors), and schemas (`quantity ≥ 0`). If the code drifts from the spec, a test fails. That's also one more kind of test to discuss.
- **The API is small enough.** With four endpoints, the usual reason to generate (keeping many endpoints in sync) doesn't apply.
- **Trade-off:** at Nuuly scale, contract-first generation is often the right call. You can say you considered it and why you chose otherwise here.

### 2. Schema migrations: Flyway, Liquibase, or `schema.sql`?

**My recommendation: Flyway.**

- **It's plain SQL.** Migrations are files like `V1__create_inventory.sql`. That fits the `JdbcClient` choice, where the SQL is always visible and nothing is hidden behind an ORM.
- **It's the common choice in Spring shops.** Spring Boot runs pending migrations automatically at startup, and it does the same against the Testcontainers database in tests, so the app and the tests always use the same schema.
- **It's versioned.** Every schema change is a numbered file in git history. That's how production teams change schemas safely, and something reviewers look for.
- **Why not Liquibase:** it's equally capable, but changes are usually written as XML or YAML changesets. That's more ceremony for one table.
- **Why not `schema.sql`:** it's fine for a demo, but it has no versioning. You can't evolve the schema without resetting the database.

The **contract gaps** (malformed body, wrong `quantity` type, SKU case, overflow) are best decided one endpoint at a time during each `/feature`, because the tests make each edge case concrete.
