## The choices behind it

1. **The Gradle project lives at the repo root, as a single module.** A multi-module build (`api/`, `domain/`, …) is overkill for four endpoints, and reviewers expect `./gradlew bootRun` to work from the root.

2. **Files are grouped by feature, and each file is named for its layer.** There are two common conventions:
   - **Package by layer:** `controller/`, `service/`, `repository/`. This is the classic Spring tutorial layout.
   - **Package by feature:** `inventory/`, `orders/`, … This is what grown-up codebases tend to use.

   We have exactly one domain, so a single `inventory/` package whose files are named `InventoryController`/`Service`/`Repository` gives us both. The controller → service → repository flow from CLAUDE.md is still obvious from the file names. It also teaches a Kotlin point: Kotlin's `internal` visibility and package-level declarations work well with feature packages.

3. **The contract stays in `docs/open_api/`.** The contract-validation test reads it from there by path, so there is only one copy to keep in sync. The alternative is moving it to `src/main/resources/` so the app serves it, but the brief doesn't ask for that.

4. **One `test` source set to start with.** Testcontainers makes the integration tests "just tests", so we don't need a separate `integrationTest` source set yet. The Gatling load test will need its own `src/gatling/` later, but only once we reach that item.

5. **No version catalog (`libs.versions.toml`).** Spring's dependency management already pins nearly every library version. A catalog adds indirection you'd have to explain without it buying us anything.

6. **Generate with Spring Initializr, then comment every line.** I'd run a `curl start.spring.io/...` command, record it in the README, and then give every generated line the teaching-mode comments. The alternative is writing the build file entirely by hand. That teaches more about Gradle, but it's easy to get plugin and version combinations subtly wrong. Initializr plus line-by-line commenting (and a walkthrough) gets most of the learning without that risk.

7. **Versions:** JDK 21 (installed), with whatever current stable Spring Boot and Kotlin Initializr offers. That is most likely **Spring Boot 4.x**, which moved to Jackson 3 and split its starters into smaller modules. We'll check at scaffold time and pin the exact versions in the README.

## 2. build.gradle.kts

**Role:** the build definition. It says which compiler and plugins to use, which libraries the app and tests need, and how tests run. It's also the most Kotlin-heavy file we have, so we'll take it in three parts. Part 1 is below.

### Part 1a: the whole file is function calls

[build.gradle.kts:2-9](build.gradle.kts#L2-L9)
```kotlin
plugins {
    kotlin("jvm") version "2.3.21"
    // Opens Spring-annotated classes: Kotlin classes are final by default, Spring needs to subclass some.
    kotlin("plugin.spring") version "2.3.21"
    id("org.springframework.boot") version "4.1.1"
    // Supplies versions from Spring Boot's BOM, so most dependencies below have none.
    id("io.spring.dependency-management") version "1.1.7"
}
```

**Kotlin: trailing lambdas.** `plugins { ... }` looks like a config block, but it's a **function call** whose only argument is a lambda (a block of code passed as a value). Kotlin has two rules here:
1. If the last argument is a lambda, it can move outside the parentheses: `plugins() { ... }`.
2. If it's the *only* argument, the empty `()` can go too: `plugins { ... }`.

So `plugins { ... }` is `plugins({ ... })`. In Java you'd write something like `plugins(spec -> { ... })`.

**Kotlin: lambda with receiver.** Inside the braces you call `id(...)` and `kotlin(...)` with no object in front. That's because Gradle runs the lambda with `this` set to a plugins-configuration object, and `id(...)` really means `this.id(...)`. A block like this, where the braces decide what `this` is, is called a **type-safe builder**. It's how Kotlin DSLs read like configuration while staying type-checked.

**Kotlin: infix functions.** `id("...") version "4.1.1"` is `id("...").version("4.1.1")`. A single-argument function marked `infix` can drop the dot and parentheses. `kotlin("jvm")` is just shorthand for `id("org.jetbrains.kotlin.jvm")`.

**What each plugin does:**
- **`kotlin("jvm")`**: compiles Kotlin to JVM bytecode.
- **`plugin.spring`**: this one matters most. Kotlin classes are **final by default**, the opposite of Java. Spring sometimes creates a *subclass* of your bean at runtime (a proxy) to wrap extra behavior around your methods, for example to begin and commit a transaction. You can't subclass a final class. This compiler plugin automatically marks classes with Spring annotations as `open`.
- **`org.springframework.boot`**: adds the `bootRun` and `bootJar` tasks.
- **`dependency-management`**: loads Spring Boot's BOM (bill of materials), a list of library versions tested together. That's why most dependencies further down have no version.

**`final` doesn't mean immutable.** They're two separate ideas:

| | Controls | Kotlin keyword |
|---|---|---|
| **final / open** | whether a class can be *subclassed*, or a method *overridden* | `open` (final is the default) |
| **mutable / immutable** | whether a *value* can change after it's set | `var` vs `val` |

A final class can hold perfectly mutable state:

```kotlin
class Counter {          // final: nobody can subclass it
    var count = 0        // but count can change freely
}
```

The Spring proxy also doesn't change any values in your class. It **wraps method calls**. Picture what Spring generates at runtime, roughly:

```kotlin
class InventoryService$$Proxy : InventoryService() {      // subclass: needs InventoryService to be open
    override fun purchase(...) {                          // override: needs purchase() to be open too
        beginTransaction()
        try { super.purchase(...); commit() }
        catch (e: Exception) { rollback(); throw e }
    }
}
```

That shows the other half of the problem: **methods are final by default too**, and the plugin opens those as well. Without the plugin, what goes wrong depends on what's final:
- **The class is final:** Spring fails *at startup* with an error like "Cannot subclass final class". That's loud and easy to find.
- **The class is open but the method is final:** Spring can create the subclass but can't override the method, so your code runs **without a transaction and without any error**. That's the dangerous case.

You were right about Java: everything is open there, so this never comes up.

**Kotlin: platform types.** Kotlin's null safety works like this: `String` can never be null, and `String?` can. The compiler forces you to handle the `?` case. But Kotlin calls a lot of Java code, and plain Java types don't say whether they can be null. Kotlin calls those **platform types**, shown as `String!`. It lets you treat one either way, and if you guess wrong you get a `NullPointerException` at runtime, just like Java.

Many Java libraries annotate their methods with `@Nullable` or `@NonNull`.

**`-Xjsr305=strict`** tells Kotlin to *trust* those annotations completely. A Java method marked `@Nullable String find()` becomes `String?` in Kotlin, so forgetting the null check is a **compile error** rather than a runtime crash. (Spring 7 uses a newer annotation style, JSpecify, that Kotlin 2.1+ already treats strictly. This flag covers libraries still using the older style.)

**`-Xannotation-default-target=param-property`** matters later, for request bodies. In Kotlin, one line like

```kotlin
data class QuantityRequest(@Min(1) val quantity: Int)
```

declares three things at once: a constructor **parameter**, a **property**, and a hidden backing **field**. So where does `@Min(1)` go? This flag puts it on the parameter and on the field, which is where validation and Jackson look for it. Without the flag, a validation annotation can land somewhere the validator never looks, and it gets **silently ignored**.

## 5. InventoryApplication.kt

**Role:** the entry point. `bootRun` or `java -jar` calls `main`, which starts Spring. Spring then finds and wires every controller, service and repository. No request ever passes through this file, but none could be served without it.

### The class

[InventoryApplication.kt:1-12](src/main/kotlin/com/robertwoolbright/inventory/InventoryApplication.kt#L1-L12)
```kotlin

import org.springframework.boot.runApplication

/**
 * Entry point of the inventory service. Component scanning starts from this package, so every
 * controller, service and repository below it is picked up automatically.
 */
@SpringBootApplication

```

**Spring: `@SpringBootApplication` is three annotations in one:**

| Annotation | Effect |
|---|---|
| `@SpringBootConfiguration` | This is a configuration class: it may declare beans, and it's what tests search for (file 7). |
| `@EnableAutoConfiguration` | Configure whatever the classpath implies: Web MVC is present, so start Tomcat; JDBC and the Postgres driver are present, so build a connection pool; and so on. |
| `@ComponentScan` | Find every `@Component`, `@Service`, `@Repository` and `@RestController` **in this package and below**, create one instance of each, and wire them together. |

**Why the file sits in the root package:** because of that scan. The future `com.robertwoolbright.inventory.inventory.InventoryController` is *below* this package, so Spring finds it automatically.

**Kotlin: a class with no body.** `class InventoryApplication`, with no `{}`. Kotlin lets you leave the braces off when there's nothing inside. Spring never calls anything on this class; it only reads its annotations. Java would need `public class InventoryApplication {}`.

**Kotlin: why `class` and not `object`?** Kotlin has `object` for singletons. But Spring wants to create configuration classes itself, and to subclass them (remember the proxies from the build file). An `object` has exactly one instance, which Kotlin creates, so it doesn't fit. And `plugin.spring` makes this class `open`, because `@SpringBootApplication` counts as a Spring annotation.

### The `main` function

[InventoryApplication.kt:14-17](src/main/kotlin/com/robertwoolbright/inventory/InventoryApplication.kt#L14-L17)
```kotlin
/** Starts Spring: builds the application context, runs Flyway migrations and starts Tomcat. */
fun main(args: Array<String>) {
    runApplication<InventoryApplication>(*args)
}
```

This small function uses four Kotlin features:

1. **Top-level function.** `main` isn't inside any class. Kotlin allows functions directly in a file. The JVM still needs a class, so the compiler generates one named after the file: **`InventoryApplicationKt`**. You saw it in the startup log earlier: `Started InventoryApplicationKt in 5.7 seconds`. In Java, `main` must be a `static` method inside a class.
   - The `import org.springframework.boot.runApplication` line up top imports a *function*, not a class. Java can only do that with `import static`.
2. **`Array<String>`** is Java's `String[]`. In Kotlin, arrays are an ordinary generic class rather than special syntax.
3. **Reified type parameter.** `runApplication<InventoryApplication>` names the class in angle brackets, the same trick as `withType<Test>` in the build file. The Java equivalent is `SpringApplication.run(InventoryApplication.class, args)`.
4. **Spread operator `*`.** `runApplication` takes `vararg args: String`: any number of individual `String`s. Our `args` is an *array* of strings. `*args` unpacks the array into separate arguments. Without the `*`, it doesn't compile. Java quietly accepts an array for a vararg; Kotlin makes you say so explicitly.

**Spring: what `runApplication` does:** it builds the application context (running auto-configuration and creating every bean), runs the Flyway migrations as part of that, starts Tomcat on port 8080, and then **returns**. `main` finishes, but the JVM keeps running because Tomcat's threads are still alive. That surprises a lot of people.

**Spring: `@TestConfiguration`** is a configuration class meant only for tests. It connects to what you just answered: this class is in `...inventory.support`, *under* the main package, so the component scan would normally pick it up. `@TestConfiguration` specifically tells the scan to **skip it**. The container exists only in tests that explicitly `@Import` it. Otherwise every test, even one that doesn't need a database, would start Postgres.

**Spring: `proxyBeanMethods = false`.** Normally Spring subclasses a configuration class (yes, another proxy), so that if one `@Bean` method calls another, you get the shared bean rather than a new copy. We have one bean and no such calls, so turning the proxy off is slightly faster and changes nothing.

**Kotlin: named arguments.** `proxyBeanMethods = false` names the parameter it sets. There are some rules around this:
- **Calling Kotlin functions:** named arguments are always allowed, e.g. `createUser(name = "Rob", admin = false)`. They're especially useful with booleans, where a bare `false` tells the reader nothing.
- **Calling Java methods:** not allowed. Java doesn't reliably keep parameter names in compiled code.
- **Java annotations** (like this one): every parameter *except* one called `value` **must** be named. `@TestConfiguration(false)` wouldn't compile, because a bare argument goes to `value`, which is a `String`.

## Wrap-up

That's the whole scaffold. What we covered:

- **The Gradle Kotlin DSL is Kotlin code.** Trailing lambdas and lambdas with receivers make `plugins { }` read like configuration. Also infix functions, reified generics (`withType<Test>`), and configurations deciding which classpath a library is on (`runtimeOnly` fails at *compile* time).

- **Null safety at the Java boundary.** Platform types, and `-Xjsr305=strict` turning a runtime NPE into a compile error.
- **Configuration comes from layered sources.** Command line beats environment variables, which beat `application.yml`. The same jar runs in every environment. Docker Compose and Testcontainers supply the connection details, so there are no credentials in the repo.
- **Spring's startup.** `@SpringBootApplication` = configuration + auto-configuration + component scan (children only, and a miss is a silent 404). `runApplication` returns while Tomcat keeps the JVM alive.
- **Test infrastructure.** `@TestConfiguration` is opt-in via `@Import`. `@ServiceConnection`, container lifecycle tied to the Spring context, context caching, and Ryuk as the cleanup safety net.
