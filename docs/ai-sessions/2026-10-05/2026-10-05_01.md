```
11	### What happens if two rows ever share the same SKU?
12	
13	<details>
14	<summary>Answer</summary>
15	
16	`findBySkuId` ends in `.list().singleOrNull()`. With two rows, `singleOrNull()` returns `null`
17	without throwing. The service then throws `SkuNotFoundException`, and the client gets
18	**404 "SKU not found: widget"** for a SKU that actually exists twice. That's a silent bug: the API
19	gives a wrong answer and nothing is logged.
20	
21	It can't happen today because `sku_id` is the **primary key**, so Postgres rejects a second
22	`widget` row. The Kotlin code is correct *because of* the database constraint. Keeping the primary
23	key is the real fix.
24	
25	If `sku_id` ever stopped being unique, the lookup would need reworking:
26	- **`.single()`** throws on two rows, so the bug would surface loudly as a 500 instead of a false 404.
27	  But it also throws on **zero** rows, which is the normal "not found" case, so on its own it would
28	  turn every missing SKU into a 500.
29	- A version that handles both cases: `val rows = ...list()`, then `null` when `rows` is empty,
30	  the item when there's one, and an error (such as `IllegalStateException`) when there are more.
31	- Which row is "right" is a data question, not a code question, so a duplicate should fail, not be
32	  picked arbitrarily with `firstOrNull()`.
33	
34	| List | `singleOrNull()` | `single()` | `firstOrNull()` |
35	| --- | --- | --- | --- |
36	| `[]` | `null` | throws | `null` |
37	| `[a]` | `a` | `a` | `a` |
38	| `[a, b]` | **`null`**, silently | throws | `a`, silently |
39

57	### How do you prevent SQL injection?
58	
59	<details>
60	<summary>Answer</summary>
61	
62	The SKU comes straight from the URL, so it's untrusted. The query uses a named parameter,
63	`WHERE sku_id = :skuId`, bound with `.param("skuId", skuId)`. `JdbcClient` runs it as a JDBC
```

---

## Step 1: Why your current code isn't enough

Say a cart has 2 × `dress` and 1 × `jacket`, and you simply call your existing service twice:

```
purchaseInventory("dress", 2)   → succeeds, dress goes 5 → 3
purchaseInventory("jacket", 1)  → InsufficientInventoryException (jacket is 0)
```

The dress is already sold. Each `removeStock` is atomic **on its own**, but the cart as a whole isn't. You've sold half a cart, and the rule was all or nothing.

**The rule:** atomic per statement isn't atomic per request. When one request changes several rows, you need a **transaction** around them.

## Step 2: What `@Transactional` does here

Put `@Transactional` on a new service function that loops over the lines and calls `removeStock` for each one:

```
BEGIN
  UPDATE dress  ... WHERE quantity >= 2   → ok, 5 → 3   (not yet visible to anyone else)
  UPDATE jacket ... WHERE quantity >= 1   → no row, so the service throws
ROLLBACK                                  → dress is back to 5, as if nothing happened
```

Three facts make this work with **no changes to your repository**:

1. **Spring opens the transaction** when the function is called and commits when it returns normally.
2. **An unchecked exception rolls it back.** Your `InsufficientInventoryException` and `SkuNotFoundException` are `RuntimeException`s. This is FAQ Q17 coming true: "`RuntimeException` matters for `@Transactional`."
3. **`JdbcClient` joins the transaction automatically.** Spring keeps the open connection on the current thread, and every `jdbcClient.sql(...)` call in that thread uses it. So `removeStock` doesn't know or care that it's inside a bigger transaction.

That third point is a good one to say out loud: *"The repository doesn't change. The service decides the transaction boundary."* It's the same split as before: the repository runs SQL, and the service decides what the business operation is.

## Step 3: The new problem is deadlock

Before this change, each row lock lasted one statement, well under a millisecond. Inside a transaction, **a lock is held until commit**. Now two carts can block each other:

| Time | Cart A: dress, jacket | Cart B: jacket, dress |
| --- | --- | --- |
| 1 | locks `dress` ✓ | |
| 2 | | locks `jacket` ✓ |
| 3 | wants `jacket` → waits for B | |
| 4 | | wants `dress` → waits for A |
| 5 | **both wait forever** | |

Postgres notices after about a second (`deadlock_timeout`), kills one transaction with an error, and that customer's checkout fails with a 500.

**The fix is one line: sort the lines by `skuId` before updating.** Both carts then lock `dress` before `jacket`. Cart B waits at its *first* lock, while it holds nothing, so there's no cycle. A always finishes, then B goes.

It's the same rule as a database textbook's "lock ordering", or Java's "always acquire locks in the same order". If you can explain it with that table, you'll sound senior.

**Merge duplicates too:** if the cart has `dress` twice (2 + 1), combine it into one line for 3. It's clearer, and it's one row lock instead of two.

**"Do you need `SERIALIZABLE` isolation?"** No. Your guarantee comes from how an `UPDATE` behaves, not from the isolation level. Under the default `READ COMMITTED`, a waiting `UPDATE` re-checks its `WHERE` against the latest committed value once the lock is free. fun checkout(lines: List<CartLine>): List<InventoryItem> { ... }

## 2. How it works: a proxy

At startup, Spring sees the annotation and **doesn't give the controller your `InventoryService` directly**. It creates a subclass, a **proxy**, that wraps every `@Transactional` function:

```
controller ──► proxy.checkout(...)
                 │ 1. BEGIN, and bind the connection to the current thread
                 │ 2. call the real InventoryService.checkout(...)
                 │ 3a. returned normally        → COMMIT
                 │ 3b. threw RuntimeException   → ROLLBACK, rethrow
                 ▼
```

Step 1 is why your repository needs no changes. `JdbcClient` asks "is there a connection bound to this thread?" before each query, finds the transaction's connection, and uses it. Every `removeStock` call inside `checkout` runs in the same transaction.

Everything confusing about `@Transactional` follows from this picture.

## 3. Traps that follow from the proxy

**a) Calling it from inside the same class does nothing:**

```kotlin
@Service
class InventoryService(...) {
    fun placeOrder(lines: List<CartLine>) = checkout(lines)  // calls this.checkout, NOT the proxy

    @Transactional
    fun checkout(lines: List<CartLine>) { ... }               // no transaction when reached this way
}
```

The proxy only sees calls coming **from outside**. Internal calls go straight to the real object, so there's no transaction and **no error**: it silently runs without one. Fix: put the annotation on the function the controller calls.

**b) Kotlin classes are `final`**, and a proxy is a subclass. The `kotlin("plugin.spring")` line in your `build.gradle.kts` makes classes annotated with `@Service`, `@Component`, `@Transactional` and similar annotations `open` automatically. Without it, Spring couldn't build the proxy.

**c) It's tied to one thread.** The connection is bound to the current thread. Work you hand to another thread (an executor, a coroutine on another dispatcher) is **outside** the transaction. Your own `InventoryConcurrencyTest` documents this:

> `@JdbcTest`'s rolled-back transaction belongs to the test thread only: rows it inserts stay invisible to the worker threads, and the workers' commits escape the rollback.

That's trap (c), and you've already hit it and worked around it with `@SpringBootTest`.

## 4. Rollback rules, plus a Kotlin trap

By default, Spring rolls back on **unchecked** exceptions (`RuntimeException`, `Error`) and **commits** on checked ones.

Kotlin has no checked exceptions, but Java's still exist at runtime. If a Kotlin function throws `java.io.IOException` (a checked exception in Java), Spring **commits** the half-done work. Kotlin won't warn you. The safe habit in Kotlin:

```kotlin
@Transactional(rollbackFor = [Exception::class])
```

Your domain exceptions extend `RuntimeException`, so they roll back by default.

## 5. The settings you might be asked about

| Setting | Default | What it means |
| --- | --- | --- |
| `propagation` | `REQUIRED` | Join the caller's transaction if one is open, otherwise start one. `REQUIRES_NEW` pauses the outer transaction and runs a separate one: useful for an audit log that must be saved even when the order rolls back. |
| `isolation` | the database's default (Postgres: `READ COMMITTED`) | How much concurrent transactions see of each other. You don't need to raise it: the atomic `UPDATE` re-checks the latest value anyway. |
| `readOnly` | `false` | A hint for read-only work. Some drivers and pools can route it to a read replica. |
| `timeout` | none | Roll back if it runs longer than N seconds. |
| `rollbackFor` | unchecked only | See the Kotlin trap above. |

## 6. Where it belongs, and what it costs

- **On the service layer**, because the service knows what one business operation is ("a checkout"). Not on the controller, which only speaks HTTP, and not on the repository, where each function is one statement.
- **Keep it short.** Every row you update stays locked until commit. Never call another service over HTTP, or send an email, inside a transaction: you'd hold locks for the length of a network call. If the email fails, should the order roll back? Do that work after the commit (the outbox, Q7).
- **One statement doesn't need it.** That's why your code has none today: Postgres runs every statement in its own implicit transaction, so `removeStock` is already all or nothing on its own.

## 7. The alternative: `TransactionTemplate`

If the proxy rules feel too magical, Spring also lets you write the transaction explicitly:

```kotlin
transactionTemplate.execute {
    // everything here is one transaction; an exception rolls it back
}
```

No proxy, so no self-call trap, and the boundary is visible in the code. Mentioning that you know both and when you'd choose each is a strong signal.
