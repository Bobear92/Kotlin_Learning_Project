
**Acceptance criteria**
- [ ] `POST /inventory/{skuId}/purchase` with `{"quantity": n}` and enough stock returns `200` JSON `{"skuId", "quantity": <remaining>}`
- [ ] Buying exactly the stock on hand leaves quantity `0`, and the row stays, so `GET` still shows it
- [ ] Buying more than is on hand returns `400` `text/plain`, and stock is unchanged (no partial fill)
- [ ] An unknown SKU returns `404` `text/plain` `SKU not found: <skuId>`
- [ ] Invalid requests return `400` `text/plain` with the same rules as `POST /inventory/{skuId}` (`quantity < 1`, malformed/strict JSON, wrong Content-Type). Your existing `@RestControllerAdvice` handlers should cover these for free, and the tests will prove it.
- [ ] Never oversells under concurrency: N > S concurrent purchases → exactly S succeed, final quantity is 0, never negative

**Things I'm settling by convention** (tell me if you disagree):
- If a request is both invalid and for an unknown SKU (e.g. `quantity: 0` on a missing SKU), it gets **400**. Spring validates the body before your code runs, and this matches how POST already behaves.
- SKU matching stays exact and case-sensitive, as decided for POST.

**Your decisions:** one CTE statement for the purchase, and the 400 body is `Insufficient inventory for <skuId>`.

That one statement has **three** outcomes: purchased, SKU missing, or not enough stock. A nullable return (`InventoryItem?`, like `addStock`) can only express two, so the repository needs a return type that can hold three. In Kotlin that's a **sealed interface**.

### Files you'll write (request-path order)

|---|---|---|---|
| 1 | `inventory/PurchaseResult.kt` (new) | model | `sealed interface PurchaseResult` with three cases: `Purchased(val item: InventoryItem)` (a data class), `SkuNotFound` and `InsufficientStock` (both `data object`s) |
| 2 | `InventoryRepository.removeStock(skuId: String, quantity: Int): PurchaseResult` | repository | One SQL statement.
