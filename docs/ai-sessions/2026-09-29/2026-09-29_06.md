I wrote the tests, so now I'll explain. The controller, service and repository tests are one test per behavior you've already explained: happy path, last unit, 400, 404, case sensitivity, quantity below 1, bad body, wrong content type, and the 400-before-404 ordering. The one worth your interview time is the **concurrency test**, the proof behind "a purchase never oversells".

You saw the `race` helper in the receive walkthrough: N threads line up behind a start gate and hit the database at the same moment. Here's the core purchase test:

[InventoryConcurrencyTest.kt:97-118](src/test/kotlin/com/robertwoolbright/inventory/inventory/InventoryConcurrencyTest.kt#L97-L118)
```kotlin
@RepeatedTest(5)
fun `concurrent purchases never sell more than the stock`() {
    val stock = 10
    jdbcClient.sql("INSERT INTO inventory (sku_id, quantity) VALUES ('widget', ?)").param(stock).update()
    val threads = 50

    val results = race(threads) { inventoryRepository.removeStock("widget", 1) }

    val failures = results.mapNotNull { it.exceptionOrNull() }
    assertTrue(failures.isEmpty(), "purchases failed: $failures")
    val outcomes = results.map { it.getOrThrow() }
    val remaining = outcomes.filterIsInstance<PurchaseResult.Purchased>().map { it.item.quantity }.sorted()
    assertEquals((0 until stock).toList(), remaining)
    assertEquals(threads - stock, outcomes.count { it == PurchaseResult.InsufficientStock })
    assertEquals(0, quantityOf("widget"))
}
```

**The setup:** 10 in stock and 50 buyers of 1 each, all released together. Demand is five times supply.

**The four assertions, from weakest to strongest:**
1. `failures.isEmpty()`: no thread got a database error. Contention produces waiting, not crashes.
2. `count { it == InsufficientStock } == 40`: exactly 40 buyers were refused.
3. `quantityOf("widget") == 0`: the stock ends at 0, not below.
4. **`remaining == [0, 1, 2, …, 9]`.** This is the clever one. Each successful buyer gets back the stock left *after* their purchase. If every unit was sold exactly once, the ten winners saw 9, 8, 7, … 0, one each. If two buyers had both read 10 and both written 9 (a lost update), you'd see `9` twice and the list wouldn't match. So this checks not just the final total but that **every single sale was accounted for**.

**Kotlin in there:**
- `filterIsInstance<PurchaseResult.Purchased>()` keeps only the `Purchased` results **and** narrows the list's type, so `.item` compiles on the next call. It's a smart cast applied to a whole list.
- `results` is a `List<Result<T>>`. Kotlin's `Result` wraps "a value or an exception"; `runCatching` in the helper makes one. `exceptionOrNull()` and `getOrThrow()` unpack it.
- `@RepeatedTest(5)`: races are nondeterministic, so each test runs five times to give a bad interleaving more chances to show up.

**What it *really* proves:** it's the table from the repository notes, run for real. Postgres locks the row; the second `UPDATE` waits, then **re-checks `quantity >= 1` against the newly committed value**. That re-check is what stops buyer #11.

The other two purchase tests extend this: **uneven sizes** (buyers of 1 to 7 units, check that sold ≤ stock and the balance is exact) and **restocks mixed with purchases** (every +3 and every successful −5 adds up exactly).

| | Buyers 1–12 (all at once) | Buyer 13 (a bit later) |
| --- | --- | --- |
| Read | all read `10` | reads `9` |
| Kotlin check | `10 >= 1` passes for all | passes |
| Write | all run `SET quantity = 9` | `SET quantity = 8` |
| Returned | twelve `Purchased(widget, 9)` | `Purchased(widget, 8)` |

So `remaining` comes back as something like `[8, 9, 9, 9, …]`: **more than 10 "successful" sales**, most of them lost updates. The stock may even end above 0 while more units were "sold" than ever existed.

And here's the callback to earlier: **the `CHECK (quantity >= 0)` doesn't save you here either.** Every write sets a value like 9 or 8, which is ≥ 0. The oversell happens without the stock ever going negative. It's the same lesson as the `-5` case. The constraint protects one invariant, not correctness in general. What actually prevents this is doing the check **inside** the write (`WHERE quantity >= :requested_quantity` plus a relative `quantity = quantity - :requested_quantity`), which is why the one-statement design matters.

## Wrap-up

What we covered:
- **Request pipeline order:** routing → `@RequestBody` (content type, JSON) → `@Valid` → your function → database. That order is why a bad body on a missing SKU is a 400, not a 404.
- **Input validation lives in the application:** the database `CHECK` protects "stock ≥ 0". It doesn't catch a negative purchase or a lost update.
- **Sealed interfaces:** a closed set of outcomes (`data class` when a case carries data, `data object` when it doesn't) lets `when` be checked for completeness without an `else`, so adding a case breaks the build right where it needs handling.
- **Two kinds of `when`:** with a subject (like `switch`: `is` for types, equality for objects) and without one (like an if/else-if chain: first true branch wins, `else` required). Smart casts show up in both.
- **The one-statement CTE:** the check happens inside the `UPDATE`, one snapshot per statement, `RETURNING` as the only way to see the new value, and `NULL` ≠ `0` (`javaObjectType`).
- **Layers:** the repository reports facts, the service throws domain exceptions, and the handler maps them to HTTP. The concurrency test proves "every unit sold exactly once".
