```yaml

```

**Spring:** auto-configuration builds a `DataSource` from *connection details*. Usually those come
from `spring.datasource.url`, `username` and `password`. Docker Compose support and
`@ServiceConnection` both register a `JdbcConnectionDetails` bean that takes priority over those
properties, so the database is wherever the container is.

**Why:** this means no hard-coded port and no password in a committed file.

**Spring: property sources.** This file is only one layer of configuration. Spring reads several
sources, and a higher one overrides a lower one:

```text
1. Command-line arguments      java -jar inventory.jar --spring.datasource.url=...
2. Environment variables       SPRING_DATASOURCE_URL=...
3. application.yml             (inside the jar)
4. Spring Boot's defaults
```

So production never edits this file. It sets environment variables, and Spring maps
`SPRING_DATASOURCE_URL` to `spring.datasource.url` (uppercase to lowercase, `_` to `.`), which
is called **relaxed binding**. The same jar runs everywhere; only the environment changes (the
"config" rule of the twelve-factor app), and passwords come from the server's secret store
instead of git.

Try it: `$env:SPRING_APPLICATION_NAME = "hello-override"; ./gradlew bootRun` makes every log
line say `[hello-override]`, even though this file says `inventory`.

Your Jackson answers are right. The "strict type matching" phrasing for scalar coercion is good. The case that matters for us is a **string** turning into a number: `{"quantity": "5"}` would quietly become `5`. Your float example, `12.5` → `12`, is exactly the one the notes use.

**Question 1 is the gap.** The validation starter isn't about how numbers are read. It's about whether anyone *checks* them at all.

Think of it this way: `@Min(1)` is a sticky note on the field that says "must be at least 1". An annotation is only metadata. On its own it does nothing, much like a `// Why:` comment that the compiler skips. Something has to go looking for the sticky notes and enforce them.

- `@Min` comes from the **Jakarta Validation API**, which is just the annotation definitions.
- The starter adds **Hibernate Validator**, the engine that actually reads those annotations. With it on the classpath, Spring Boot auto-configures a `Validator` bean, and Spring MVC runs it on any `@RequestBody` marked `@Valid`.

**Without the starter:** the code still compiles and the app still starts. `@Min(1)` gets silently ignored and there's no error anywhere. That's the dangerous part.

| Annotation | Comes from | Filled by |
|---|---|---|
| `@PathVariable` | the **URL** | Spring matches the `{skuId}` placeholder |
| `@RequestBody` | the **body** | Jackson converts JSON into an object |

### Fix 2: the two annotations are the two gates

"Jackson validations" mixes the two gates again. Each annotation belongs to one gate:

- `@RequestBody` → **Gate 1.** Jackson builds the object and checks the **type** (your YAML settings apply here).
- `@Valid` → **Gate 2.** Bean Validation checks the **value** (`@Min(1)`).

Jackson reads; Bean Validation validates.

### Gap 1: why only `.quantity` goes to the service

`InventoryQuantity` is an **HTTP shape**: it exists because the contract says the body is `{"quantity": ...}`. The service is **business logic**, so it takes plain `String` + `Int` and knows nothing about web classes. That means:

- Something other than HTTP (a scheduled job, a message queue, a test) can call `receiveInventory("ABC-123", 5)` without building a web object.
- If the request body shape ever changes, only the controller changes.

It's the same reason the service throws exceptions instead of returning `ResponseEntity`: **HTTP stays in the controller layer.**

### Gap 2: why 200, not 201

REST convention would say `201 Created` for a new resource. But this endpoint does two things: it creates a SKU **or** adds to an existing one. ### Does it slow things down?

That's a good instinct, and the answer is **no. It's actually faster than the alternative:**

1. **The wait is tiny.** The lock is held only while one statement runs, typically well under a millisecond. At 100 TPS spread across many SKUs, requests almost never collide.

## Design and failure modes

### What happens if two rows ever share the same SKU?

<details>
<summary>Answer</summary>

`findBySkuId` ends in `.list().singleOrNull()`. With two rows, `singleOrNull()` returns `null`
without throwing. The service then throws `SkuNotFoundException`, and the client gets
**404 "SKU not found: widget"** for a SKU that actually exists twice. That's a silent bug: the API
gives a wrong answer and nothing is logged.

It can't happen today because `sku_id` is the **primary key**, so Postgres rejects a second
`widget` row. The Kotlin code is correct *because of* the database constraint. Keeping the primary
key is the real fix.

If `sku_id` ever stopped being unique, the lookup would need reworking:
- **`.single()`** throws on two rows, so the bug would surface loudly as a 500 instead of a false 404.
  But it also throws on **zero** rows, which is the normal "not found" case, so on its own it would
  turn every missing SKU into a 500.
- A version that handles both cases: `val rows = ...list()`, then `null` when `rows` is empty,
  the item when there's one, and an error (such as `IllegalStateException`) when there are more.
- Which row is "right" is a data question, not a code question, so a duplicate should fail, not be
  picked arbitrarily with `firstOrNull()`.

| List | `singleOrNull()` | `single()` | `firstOrNull()` |
| --- | --- | --- | --- |
| `[]` | `null` | throws | `null` |
| `[a]` | `a` | `a` | `a` |
| `[a, b]` | **`null`**, silently | throws | `a`, silently |

## API design and validation

### How does your API validate input?

<details>
<summary>Answer</summary>

Two checks, in order, each with its own 400 message:

| Check | Runs in | Catches | Response |
| --- | --- | --- | --- |
| **1. Is it an `Int` at all?** | Jackson, while reading the body | malformed JSON, missing or `null` `quantity`, `"5"`, `1.5`, a number too big for `Int` | 400 `Invalid request body` |
| **2. Does the value follow the rules?** | Bean Validation (`@Min(1)` + `@Valid`), after Jackson succeeds | `0`, `-5` | 400 `quantity must be at least 1` |

Jackson has to build the object before validation can check it, so `{"quantity": 0}` passes check 1
and fails check 2, and `{"quantity": 1.5}` never reaches check 2. The messages tell the client
different things: "you didn't send valid input" vs "your input broke a rule".

Jackson's defaults are lenient: they'd turn `"5"` into 5 and silently truncate `1.5` to 1. Two
settings in `application.yml` turn that off (`accept-float-as-int`, `allow-coercion-of-scalars`),
because a stock count must be exactly what the client sent, never a guess. A wrong `Content-Type`
is a third, earlier check (400 instead of Spring's 415, which the contract doesn't list).

Notes: [application.yml, strict JSON](notes/main/resources/application.yml.md#strict-json-the-jackson-block)
