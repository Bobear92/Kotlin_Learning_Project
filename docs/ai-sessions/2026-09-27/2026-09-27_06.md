### Claude

That's a solid explanation. You covered all three pieces. Here are a few corrections and the parts the code doesn't show.

**1. Who "solves" the null case.** You said "we have to solve the null case for this function." The more precise version: `findBySkuId` doesn't solve the null case, it *reports* it. The `?` means the **caller** has to deal with it. The compiler won't let the service use `.quantity` on an `InventoryItem?` until it has handled `null`. That split is deliberate:

- The **repository** says "no row" by returning `null`. That's a normal answer to a lookup, not an error.
- The **service** decides what "no row" *means* for this endpoint, which is a 404. Later, the purchase endpoint will make the same lookup and may give a different answer.

Java comparison: every Java reference can be null and nothing warns you. Kotlin puts that information in the type itself. At runtime `InventoryItem?` is just a normal reference, with no wrapper object like `Optional`.

**2. What `.param` actually does.** You're right that it stops SQL injection. Here's how:
- `JdbcClient` rewrites `:skuId` into JDBC's `?` and runs a `PreparedStatement`.
- Postgres receives the SQL text first and parses it, and only then receives the value.
- Because the query's structure is fixed before the value arrives, a SKU like `x' OR '1'='1` can't change it. It's just a string that matches nothing.

Compare the version we avoided: `"... WHERE sku_id = '$skuId'"` pastes the value into the SQL text, and the attacker's quote closes yours. `:skuId` (named) instead of `?` (positional) is only for readability.

**3. A `singleOrNull` detail worth knowing for the interview.** It has three cases, not two:

| List | `singleOrNull()` | `single()` |
| --- | --- | --- |
| `[]` | `null` | throws |
| `[a]` | `a` | `a` |
| `[a, b]` | **`null`**, silently | throws |

So if two rows ever matched, the SKU would look *missing* and no error would be raised. Your reasoning is what makes this safe: `sku_id` is the primary key, so two rows can't exist. The Kotlin code is correct *because of* the database constraint.

**4. Something you didn't mention:** the lambda uses **named arguments**, `InventoryItem(skuId = ..., quantity = ...)`, while `findAll` passes them by position. Both compile to the same call. Named arguments make it impossible to swap two values by accident.

### Claude

You've got the role right: it's thrown by the service when the repository returns `null`. The reason you gave for a custom exception is the part I'd push back on. It's also the part most likely to come up in the interview.

**"So we can be more detailed in the error message"** isn't the real reason, because Spring's built-in exception takes a message too:

```kotlin
throw ResponseStatusException(HttpStatus.NOT_FOUND, "SKU not found: $skuId")
```

That's just as detailed. The real reasons are about **which layer knows about HTTP**:

1. **The service shouldn't speak HTTP.** `ResponseStatusException(HttpStatus.NOT_FOUND)` puts a status code inside the service. `SkuNotFoundException` only says *what* went wrong ("this SKU doesn't exist"). The handler decides how that looks over HTTP. It's the same split as the repository returning `null` and the service deciding it means "not found": each layer answers one question.
2. **Reuse.** The purchase endpoint will throw the same exception for a missing SKU, and the same handler will map it. There's one place to change if the 404 format ever changes.
3. **The contract.** `ResponseStatusException` produces a JSON error body by default, and inventory.yaml requires `text/plain`. That's why you have a handler at all.

A short way to put it: *the exception names the problem, and the handler picks the response.*

**The two Kotlin pieces you skipped:**

**`: RuntimeException("...")`** means "extends `RuntimeException`" plus the `super(...)` call, in one step. Java version:

```java
public class SkuNotFoundException extends RuntimeException {
    public SkuNotFoundException(String skuId) {
        super("SKU not found: " + skuId);
    }
}
```

That's six lines in Java and one in Kotlin. The parentheses after `RuntimeException` are required, because Kotlin always makes you say which superclass constructor runs. Why `RuntimeException` and not `Exception`: Kotlin has no checked exceptions, so neither would force a `try/catch`. But `@Transactional` rolls back by default only on unchecked exceptions, which will matter once purchases write to the database.

**`skuId: String` with no `val`** makes it a *plain constructor parameter*. It exists while the object is being built (it's used in the `super` call's message), and then it's gone. `ex.skuId` won't compile. With `private val jdbcClient` in the repository, the `val` turns the parameter into a field that lives as long as the object does. Here the SKU only needs to survive inside the message text, so there's no field.

**The string template you highlighted:** `"SKU not found: $skuId"` is Java's `"SKU not found: " + skuId`. For anything more than a bare name you need braces, `"${item.skuId}"`, because `"$item.skuId"` would insert `item` and then the literal text `.skuId`.

## Wrap-up

What we covered:
- **Nullable types as honest contracts.** `InventoryItem?` passes the "maybe" up. The compiler only objects when a "maybe" is used as a "definitely". Elvis + `throw` (type `Nothing`) turns it into a definite value or an exception.
- **Each layer answers one question.** The repository says "no row" (`null`), the service says "that's an error" (`SkuNotFoundException`), and the handler says "that's a 404 `text/plain`". `private val` makes the compiler enforce the layering.
- **Storage vs visibility.** `val` keeps a constructor parameter on the object, and `private` limits who can read it. They're two separate settings.
- **How Spring handles exceptions.** Spring catches everything and asks its resolvers in order. `@RestControllerAdvice` gets custom exceptions handled before they fall through to the default 500.
- **Compile time vs startup vs first request.** Strings (paths, SQL, column names) are invisible to the compiler, so only tests that make real requests catch those bugs.
- **Tests need decoys.** A single-row table can't prove a lookup filters correctly.
