## Step 1: The contract

```yaml
/inventory/{skuId}:
  parameters:
    - name: skuId, in: path, required: true, schema: string (example CW-XYCS-BM-01)
  get:
    description: Returns the current quantity on hand for the specified SKU. Returns 404 if the SKU does not exist.
    operationId: getInventory
    responses:
      '200': application/json → InventoryItem { skuId: string, quantity: integer ≥ 0 }
      '404': text/plain → Error (a plain string)
```

**Acceptance criteria**
- [ ] `GET /inventory/{skuId}` for an existing SKU returns **200**, `application/json`, with `{"skuId": "...", "quantity": n}`.
- [ ] A SKU with zero stock still exists, so it returns **200** with `quantity: 0`, not 404.
- [ ] A SKU that doesn't exist returns **404**, `text/plain`, with a plain string body (not JSON).
- [ ] SKU matching is exact and case-sensitive (README decision, 2026-09-24): if only `widget` exists, `WIDGET` returns 404.
- [ ] `GET /inventory` still behaves as before (its tests stay green).

**Ambiguities, which need your call:**

1. **The exact 404 message.** The contract only gives an example for the 400 error ("Insufficient inventory"). I suggest **`SKU not found: <skuId>`**, because including the SKU helps debugging and the purchase 404 can reuse it. Plain `SKU not found` would also be fine.
2. **How the 404 is produced.** This is a real design choice:
   - **(a) The controller returns `ResponseEntity<*>`.** It builds either the 200 or the 404 itself. It's simple, but every endpoint repeats the not-found logic, and the return type loses its precise type.
   - **(b) Custom exception + `@RestControllerAdvice` (recommended).** The service throws `SkuNotFoundException`, and a single `@ExceptionHandler` turns it into a 404 `text/plain` response. The controller keeps a clean `InventoryItem` return type, and purchase reuses the same handler for its 404 (and later its 400).
   - *Not recommended: `ResponseStatusException`.* Spring's default error body for it is JSON, not `text/plain`, so we'd be working against the contract.

### 1. Nullable return type: `InventoryItem?`
In Kotlin, `InventoryItem` means "never null", and the compiler enforces it. Adding `?` makes it `InventoryItem?`, which means "an item, or null". It's the same idea as Java's `@Nullable`, except Kotlin actually enforces it: anyone who calls `findBySkuId` must handle the null case before using `.quantity`. That's why the service in step 3 will need `?:`.

You write it only in the function signature: `fun findBySkuId(skuId: String): InventoryItem? = ...`

### 2. Binding the SKU as a parameter
`findAll` had no input. This query does, and the value has to go in as a **bound parameter**, not glued into the SQL string. If you wrote `"... WHERE sku_id = '$skuId'"`, a request to `/inventory/x' OR '1'='1` would change your query. That's SQL injection.

`JdbcClient` gives you two styles:
- **Positional:** put `?` in the SQL, then call `.param(skuId)`. Your test helper `insert` uses this style, with `.params(...)` for several values.
- **Named:** put `:skuId` in the SQL, then call `.param("skuId", skuId)`. This reads better once there are several parameters.

### 3. "Zero or one row"
`.query { rs, _ -> ... }` stays exactly as it is in `findAll`. Only the last call changes. `.list()` gives a `List`, but you want a single item or `null`. Your two options:
- **`.optional()`** returns a Java `Optional<InventoryItem>`. You'd then convert it to a Kotlin nullable. Look at `Optional`'s `orElse(...)`, or Kotlin's `getOrNull()` extension.
- **`.list().singleOrNull()`** keeps the list and uses a Kotlin collection function. It returns the only element, or `null` if the list is empty (or has more than one element).

Avoid `.single()`. It **throws** when there are no rows, and the test says a missing SKU returns `null`.

My take: `.optional()` states the intent ("at most one"). `singleOrNull()` is more idiomatic Kotlin and avoids the Java `Optional`. Pick whichever you can explain in the interview.
