### Claude

Step 3 is the service: add a `getInventory` function to [InventoryService.kt](src/main/kotlin/com/robertwoolbright/inventory/inventory/InventoryService.kt). The repository and the exception are already done, so this step just connects them.

**What it has to do**

1. Take a `skuId: String` and return an `InventoryItem`. The return type is not nullable, so there's no `?`.
2. Call `inventoryRepository.findBySkuId(skuId)`. That returns `InventoryItem?`, which is `null` when the SKU doesn't exist.
3. If it's `null`, throw `SkuNotFoundException(skuId)`.

**The Book version from last session**, as a reminder:

```kotlin
fun getBook(isbn: String): Book =
    bookRepository.findByIsbn(isbn) ?: throw BookNotFoundException(isbn)
```

How it maps to yours:
- `isbn` → `skuId`
- `Book` → `InventoryItem`
- `bookRepository.findByIsbn` → `inventoryRepository.findBySkuId`
- `BookNotFoundException` → `SkuNotFoundException`

Two Kotlin points that make this one line work:
- `?:` (Elvis): "use the left side, but if it's `null`, use the right side instead."
- `throw` is an expression in Kotlin, not just a statement, so it can sit on the right of `?:`. If that side runs, the function throws instead of returning. That's how the compiler knows the result is never `null`, and why the return type can be plain `InventoryItem`.

**Three more things**

- **Import.** `SkuNotFoundException` is in the `error` subpackage, so the service needs an import for it (next to the `Service` import). VS Code will offer to add it when you type the name, or you can write it yourself. The full package is in the exception file's `package` line.

Why is InventoryItem not nullable? We just created a whole custom error for when it is null.

### Claude

Good question. Nullable and non-nullable describe two different functions here, and the exception is what connects them.

**The repository returns `InventoryItem?`.** "Not found" is a normal answer for a database query, so `findBySkuId` returns `null` and lets the caller decide what that means.

**The service decides what it means.** For this endpoint, a missing SKU is an error (a 404), not a normal result. So the service handles the `null` immediately: `?:` catches it and throws `SkuNotFoundException`. Because of that, `getInventory` never gets to *return* `null`. It has only two outcomes:

- the SKU exists → it returns a real `InventoryItem`
- the SKU doesn't exist → it throws, and nothing is returned at all

Neither outcome returns `null`, so the honest return type is `InventoryItem` with no `?`. If you wrote `InventoryItem?`, the signature would claim `null` is possible when it isn't.

**What callers get.** The controller calls `getInventory(skuId)` and can use the result directly, with no `if (item == null)` check. The "not found" case goes a different way: the exception jumps past the controller to `InventoryExceptionHandler` (step 5), which turns it into the 404 response.

In Book terms: `findByIsbn` says "here's the book, or nothing." `getBook` says "here's the book, guaranteed. If there isn't one, I'll throw instead of handing you nothing."

A Java comparison, since that's your background: in Java both methods would return `Book`, and you'd have to read the code or the docs to know whether `null` can come back. In Kotlin the `?` (or its absence) puts that in the type, and the compiler enforces it. If you took out the `?: throw ...` part, a non-nullable return type would fail to compile, because the compiler can see a `null` might get through.
