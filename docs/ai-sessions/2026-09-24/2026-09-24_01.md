### Claude

I'd start with **`GET /inventory`**, and make seeding part of how we test it rather than a separate step first.

**Why `GET /inventory` first**
- It's the simplest endpoint in [inventory.yaml](src/main/resources/openapi/inventory.yaml): no request body, no path parameter, no 400 or 404, just `200` with an array (possibly empty).
- It still makes us build the whole stack once: the `V1__create_inventory.sql` migration (TODO says it lands "with the first feature"), the `InventoryItem` data class, a `JdbcClient` repository, the service and the controller. You can learn each layer without error handling or concurrency getting in the way.
- Every later feature reuses those layers, and the race tests will use `GET /inventory` to check final quantities.

**Why not seeding first**
- The contract never mentions seed data. On its own it would be a decision without a feature behind it.
- Tests shouldn't depend on seed data anyway. Each test inserts the rows it needs with `JdbcClient` against Testcontainers, so it controls exactly what's there, including the "empty array" case. That covers the seeding you need to test this feature.
- Once `POST /inventory/{skuId}` exists, you can fill a running app with a few `curl` calls. If we still want sample data for demos after that, it's a small decision to make then: dev-only data, probably a Flyway migration in a location only the dev profile loads. | Option | How | Trade-off |
| --- | --- | --- |
| **A. Exact match** (current) | Nothing changes | Treats the SKU as an opaque id, the way most APIs treat ids, and matches the contract literally. Keeping `W` and `w` apart is the client's job. |
