## Step 4: `InventoryService.kt`

**Where:** `src/main/kotlin/com/robertwoolbright/inventory/inventory/InventoryService.kt` (same package as the repository).

**What it needs to do:**
- Be a Spring bean, so the controller in step 5 can have it injected.
- Take the `InventoryRepository` through its constructor.
- Have one function, `listInventory()`, that returns `List<InventoryItem>` by calling `findAll()`.

**Why have a layer that only passes the call through?** Right now the service adds nothing. It's where business rules will go later: the purchase feature will check stock, refuse to oversell and choose which error to return. ### Claude

No, it doesn't need more error handling. It's supposed to be this simple. Here's why, so you can say the same thing in the interview.

**What could go wrong here?**

| Case | What happens | Handled by |
|---|---|---|
| No SKUs in the table | `findAll()` returns an empty list, and the API returns `[]` with status 200 | Nothing to do. The contract says "If no SKUs exist, returns an empty array," and your `List<InventoryItem>` already covers it. |
| A null item or null list | Can't happen: the return type has no `?` | The compiler, thanks to your row-mapper `// Why:` line |
| The database is down or the SQL fails | Spring throws a `DataAccessException` | Let it propagate. Spring turns it into a 500. |

The last case is the important one. In Java you might expect to write `try/catch` here, but:

1. **Kotlin has no checked exceptions.** Nothing makes you catch anything, and Spring's `DataAccessException` is unchecked even in Java.
2. **Catching is only useful if you can do something about the error.** If the service caught the exception, what would it return? An empty list would be a lie: the API would say "you have no stock" when really it can't tell. Rethrowing adds nothing. So let it go up.
3. **The contract only defines a 200 for `GET /inventory`.** There's no 404 or 400 because there's no input to validate. A 500 for "the database is down" is standard behavior that the contract doesn't need to spell out.

Error handling becomes the service's job in the next features. `POST /inventory/{skuId}/purchase` has to decide "SKU not found → 404" and "not enough stock → oversell refused." Those are business rules, and that's why the service layer exists. This pass-through is the placeholder that code will live in.

**Two small doc things (no formatting nits):**
- Line 8: "Use by" → "Used by". The rest of that KDoc is good: it says exactly where the service sits in the flow.
- Line 14: "Function that returns…" doesn't tell the reader anything the `fun` keyword doesn't already. Start with the verb, the way you did on `findAll`: `/** Returns every inventory item, sorted by SKU id. */`
