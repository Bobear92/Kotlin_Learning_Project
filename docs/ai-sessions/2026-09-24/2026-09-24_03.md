**4. The function needs a body.** Here's how a Kotlin function is built, compared with Java. This is a made-up example, not your function:

```kotlin
fun greet(name: String): String {

    return message
}
```


**Without `ORDER BY`, SQL guarantees no order at all.** Postgres returns rows in whatever order is cheapest for it. Your instinct is right: it is a null issue, and my `Book` example had the same bug. I got it wrong, not you. The null issue isn't about the list, though. It's about the **items in it**. Read the error closely:

```
expected 'List<InventoryItem>', actual '(Mutable)List<InventoryItem?>'
```

The `?` after `InventoryItem` means "an `InventoryItem` **or null**". So the compiler sees a list that might contain null entries, while your function promises a list of real `InventoryItem`s.

**Why it happens:** Spring 7 marks its Java code with nullability annotations, and Kotlin reads them. I checked the source of `JdbcClient` in your Gradle cache (spring-jdbc 7.0.9):

```java
<T> MappedQuerySpec<@Nullable T> query(Class<T> mappedClass);
<T extends @Nullable Object> MappedQuerySpec<T> query(RowMapper<T> rowMapper);
```

- `query(SomeClass::class.java)` is declared as "each row *might* map to null". That's because the same method also handles single-column queries like `SELECT name ...`, where a value can be SQL `NULL`. Spring can't tell your case apart, so it plays safe.
- `query(rowMapper)` keeps whatever type **your** mapper returns. If your mapper always returns a real `InventoryItem`, the list is `List<InventoryItem>`.

(The `(Mutable)` part is harmless. Kotlin can't tell whether a Java `List` is meant to be changed, so it shows both possibilities. It fits your `List` return type fine.)

**The fix: write the row mapper yourself.** A row mapper is a small function that gets one row and returns one object. In Kotlin you pass it as a **lambda**, a function written inline in `{ }`. Here's my `Book` example corrected:

```kotlin
fun findAll(): List<Book> {
    val books = jdbcClient.sql("SELECT isbn, title FROM book ORDER BY title")
        .query { rs, _ -> Book(rs.getString("isbn"), rs.getString("title")) }
        .list()
    return books
}
```

- **`{ rs, _ -> ... }`** is a lambda with two parameters. To the left of `->` are the parameters, and to the right is the result.
  - `rs` is the `ResultSet`, positioned on the current row.
  - The second parameter is the row number. We don't need it, so `_` says "ignore this".
- **`rs.getString("isbn")`** reads a column by its **database** name. For your `quantity` column you'll want `getInt`.
- **The parentheses disappear:** `.query { ... }` rather than `.query({ ... })`. When a lambda is the last argument, Kotlin lets you move it outside the parentheses, and if it's the only argument, you drop the parentheses entirely. This is called **trailing lambda syntax**, and you'll see it everywhere in Kotlin.

Because the lambda always builds a real `InventoryItem`, the list's type becomes `List<InventoryItem>`, and the mismatch goes away. It's also more explicit than mapping by name: you can see exactly which column goes into which property. That fits the "explicit SQL" reason you chose `JdbcClient` for, and it's worth a `// Why:` comment.

### Claude

`rs` stands for **ResultSet**, the JDBC object that represents the query's results, sitting on one row at a time. And yes, it's just a parameter name, so you can call it anything: `row`, `resultSet`, `r`. The lambda's parameters work like a function's parameters: the caller decides what gets passed in (here, Spring passes the `ResultSet` and the row number), and you choose what to call them.

These all do the same thing:

```kotlin
.query { rs, _ -> ... rs.getString("sku_id") ... }
.query { row, _ -> ... row.getString("sku_id") ... }
.query { resultSet, rowNum -> ... resultSet.getString("sku_id") ... }
```

`rs` is just a very common convention from Java JDBC code, so readers recognise it instantly. `row` is arguably clearer to someone new. Pick whichever reads better to you.

The two things you can't change are the **number** of parameters (Spring's `RowMapper` always passes two, so the lambda must take two, even if one is `_`) and their **types**. Kotlin infers the types from `RowMapper`, which is why you never write `: ResultSet`.

A related shortcut you'll see later: a lambda with **one** parameter can skip naming it and use `it` instead. That doesn't apply here, because this lambda has two.

### Claude

Good question, since it looks like a mistake. It's optional: Kotlin allows a comma after the last item in a list of parameters or arguments, and the code compiles either way. The official Kotlin style guide **recommends** it whenever each item sits on its own line, as your constructor parameter does. There are three reasons:

1. **Cleaner diffs.** Suppose the class later needs a second dependency. Without the trailing comma, adding it touches two lines:
   ```diff
   -    private val jdbcClient: JdbcClient
   +    private val jdbcClient: JdbcClient,
   +    private val clock: Clock
   ```
   With it, only the new line shows up:
   ```diff
        private val jdbcClient: JdbcClient,
   +    private val clock: Clock,
   ```
   The reviewers will read your git history, so small, focused diffs help.
2. **Easy reordering.** Every line has the same shape, so you can move lines around, or delete the last one, without fixing commas.
3. **Consistency.** It's what the rest of the project does. The test class's constructor has one, and so do the multi-line `listOf(...)` calls in [InventoryRepositoryTest.kt](src/test/kotlin/com/robertwoolbright/inventory/inventory/InventoryRepositoryTest.kt).

When everything fits on a single line, like `InventoryItem(val skuId: String, val quantity: Int)`, you leave it off. So the rule of thumb is: trailing comma when it's one item per line, none when it's all on one line.

(Java allows this in array initialisers but not in parameter lists, which is why it looks odd if you come from Java.)

````
## Before the SQL: contract schemas are not tables

The contract has two schemas, `InventoryItem` and `InventoryQuantity`, and it's tempting to make
a table for each. **Schemas in an OpenAPI contract describe JSON that travels over HTTP, not
database tables.** The database is an implementation detail the contract never sees.

| Schema | Used as | Direction | Stored? |
| --- | --- | --- | --- |
| `InventoryQuantity` `{quantity}` | request body of both `POST`s | client → API | No. It's the *input* to an operation ("add 5"); the SKU comes from the URL path. |
| `InventoryItem` `{skuId, quantity}` | every `200` response | API → client | Yes. One row = one `InventoryItem`. |

So there is **one table**. In Kotlin both schemas become classes: `InventoryItem` now, and
`InventoryQuantity` as a request-body class with the `POST` feature. Classes match the contract;
tables match what needs storing. In bigger systems the two drift apart. An API response is
often assembled from several tables, and tables hold columns (timestamps, internal ids) that the
contract never shows.
````
